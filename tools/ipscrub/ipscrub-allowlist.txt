# DNS ROOT NAMESERVER -- c.root-servers.net, IPv4 and IPv6.
#
# HOW THEY GOT HERE. Not from prepush-preview. These are the two distinct
# values behind the 6 occurrences the binary scan reported on 2026-08-07:
#     python3 tools/ipscrub/ipscrub.py scan-paths \
#         android/app/src/main/jniLibs/arm64-v8a/libxray.so \
#         android/app/src/main/jniLibs/x86_64/libxray.so \
#         installer/windows/dependencies/xray.exe
# -- the same pair once each, in three separately compiled binaries. The lane
# that added binary scanning declined to allowlist them and left the call to
# the operator. Triaged and decided 2026-08-07; evidence below.
#
# WHAT THEY ARE. c.root-servers.net -- the C root nameserver, operated by
# Cogent Communications. Root HINTS, not this project's resolvers: they are
# published by IANA and ship inside every `named.root` / `root.hints` file, in
# BIND, Unbound, Knot and dnsmasq. Third-party operated and among the most
# republished addresses on the internet, exactly like the resolvers above.
#
# WHY THEY ARE IN OUR TREE -- established, not assumed. Both are compile-time
# string constants in UPSTREAM Xray-core:
#   * the three blobs are produced by tools/build_xray_engine.sh from a clean
#     clone of XTLS/Xray-core at the pinned tag v26.9.30;
#   * the Go build stamp inside each reads `path github.com/xtls/xray-core/main`;
#   * resolving the .rodata references through .gopclntab attributes BOTH
#     literals to `github.com/xtls/xray-core/app/dns.checkRoutes` and the two
#     closures beside it -- upstream's own package, not any code of ours;
#   * all three targets (arm64 ELF, x86_64 ELF, Windows PE) carry the identical
#     pair, which a value injected into one artifact would not.
#
# WHAT THE CODE DOES WITH THEM, AND WHY IT IS NOT A DNS LEAK. checkRoutes dials
# each address with network "udp4" / "udp6" and calls Close() on the result
# immediately -- no Read, no Write, no DNS message is ever constructed. A UDP
# dial is a kernel route lookup plus a source-address bind; it puts ZERO bytes
# on the wire. The two booleans it sets are "does this host have a usable v4 /
# v6 route", which is what selects the query strategy. Nothing is ever sent to
# either address, so no query escapes the tunnel by way of these constants.
#
# They therefore disclose nothing about this project's infrastructure. If a
# future scan reports a DIFFERENT address from these binaries, that is not this
# entry: re-triage it, because a vendored blob carrying a value that is not
# upstream's is an incident, not an allowlist question.
# ---------------------------------------------------------------------------
192.33.4.12             # c.root-servers.net -- upstream Xray-core route probe
2001:500:2::c           # c.root-servers.net, IPv6 -- same probe, same function
