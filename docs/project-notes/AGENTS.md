# Win's VPN Project Operating Notes

- Permanent execution policy: keep independent work in parallel whenever safe.
  Prefer six Cursor/Grok 4.6 Extra High lanes for bounded review or implementation
  slices, with Codex actively supervising integration and retaining the
  highest-risk critical path. Refill completed lanes while useful disjoint work
  remains. Fable 5 and GLM 5.3 are consultation-only; Daybreak Blue performs the
  final defensive code review before a fresh Google Cloud proof deployment.
  Never claim a lane is running without checking the process or agent state.
- GitHub is backup storage only. Do not use GitHub Actions, hosted runners,
  Releases, deployment environments, or GitHub as a release gate. Do not push,
  publish, or create remote state unless the owner explicitly authorizes that
  exact action. Local tests and independently captured target evidence are the
  release authority.
- FIRST THING IN A FRESH CLONE, before any `git push`: run `sh tools/ipscrub/install-hooks.sh`. It installs the pre-push disclosure gate, which refuses to upload node addresses or WireGuard private/preshared keys to the remote. `.git/hooks/` is not version controlled, so a clone has NO gate until you run this -- and an unguarded push is not noticed until after it has happened. It is safe to re-run, it verifies itself, and it will not silently displace a pre-push hook it did not write. See `tools/ipscrub/README.md`.
- For Android app changes, always test on the connected USB-debugging phone before closing the task.
- Before each Android test, uninstall the existing package first: `adb uninstall org.winsvpn.app`.
- Install the latest release APK from `build/app/outputs/flutter-apk/app-release.apk`, launch it, and inspect `adb logcat` for startup or VPN errors.
- Treat the connected phone test as the reference smoke test for shared app logic that will later be mirrored to Windows, Linux, macOS, and iOS where applicable.
- From Windows, run Apple-only commands through `tools/remote_mac.ps1`; use its `BuildIOS`, `BuildMacOS`, `Simulators`, or `VerifyApple` action as appropriate.
- Before an Apple build, ensure the changed source files exist in `/Users/winsvpn/Downloads/wins_vpn` on the Mac. Git remains the preferred cross-machine source of truth; use targeted `scp` only for uncommitted files that must be tested before commit.
- Never run concurrent `flutter pub get`, `flutter test`, or platform builds from the same project directory across Windows, WSL/Linux, Android, or Apple lanes. Flutter rewrites `.dart_tool/package_config.json` with host-specific paths. Use the platform release builder's lock or a manifest-verified isolated copy/worktree for every parallel lane.
- Do not delete or override an active `.dart_tool/winsvpn-release-build.lock`. If a release build owns the shared root, move independent testing to an isolated copy instead of invoking raw Flutter commands there.
- This project is worked on by multiple AI models/tools across sessions (Cursor, Codex, etc.), so it stays portable via living handoff briefs instead of relying on any one model's memory: `FINAL_RECOMMENDATIONS_FIX_HANDOFF_20260722.md` tracks the `Final Recommendations.md` security-fix backlog; `NEW_MACBOOK_M5_PRO_CONTINUATION_20260721.txt` tracks broader Mac-migration/AICORE/cross-machine context. Whichever model is driving, after finishing each milestone (not each tiny edit) append a short dated entry to the relevant brief -- what changed, why, how it was verified, what's left -- instead of creating a new dated file each time. Read the relevant brief fully before resuming work in either area.
- OWNER-DECISIONS-NEEDED GOVERNANCE (v1, 2026-09-03). This is the canonical clause; other project documents incorporate it by reference and must not paraphrase it into a weaker rule. In this clause, "owner" means the human owner acting directly; no delegate, arbiter, model, agent, or standing authority may accept, reject, apply, remove, narrow, amend, or repeal a label under it. An agent may propose the `OWNER-DECISIONS-NEEDED` label only by naming the item and its dependent scope in writing. A proposed label blocks work in that scope that depends on the item until the owner accepts or rejects the proposal; unrelated work continues. Owner acceptance fixes the scope. An owner-applied label blocks dependent work in that scope until the item is satisfied and durably recorded; the durable satisfaction record lifts the block even if label housekeeping remains. If the owner applies a label without fixing its scope, all work that plausibly depends on the item is blocked until the owner fixes the scope. Before any owner decision, the proposing agent must present the named item, options, consequences, and proposed scope to the owner in one place. A broad-batch approval, general instruction to proceed, standing delegation, delegated-model ruling, approval of defaults, or other non-item-specific communication cannot accept, reject, remove, narrow, or satisfy the item, regardless of delegation scope. Only a direct, item-specific owner decision after that presentation may do so. An acceptance, rejection, removal, scope change, or substantive resolution becomes effective only after a durable repository ruling or decision record names the item, action or decision, scope, date, and direct owner-message provenance. This clause applies only to items first proposed on or after the commit that introduces it. It reopens nothing proposed or decided earlier, including any part of `OWNER_RATIFICATION_RELEASEPYTHON_V2_AND_DEPLOYMENT_GOVERNANCE_20260903.md`. The owner may amend or repeal this clause only through a direct, non-delegable instruction that explicitly identifies this canonical clause and states the change; the amendment or repeal becomes effective only after a durable repository ruling records that instruction, date, and direct owner-message provenance.
- RULED INVARIANTS. `docs/rulings/RULINGS.lock` lists decisions made by the delegated authority (currently: macOS `enforceRoutes = true`, single source `WinsMacRoutePosture` in `macos/Runner/RouteAudit.swift`). The DISPATCHER runs `tools/verify_rulings.sh` after every lane merge and before any release build; a non-zero exit means a ruled decision was changed without a ruling event, and the merge or release stops there. Lanes must not edit `RULINGS.lock` or any line it guards; changing either requires a new dated ruling document first. This exists because on 2026-08-10 a lane silently reverted the ruled macOS `enforceRoutes` posture and the tree carried an open route-injection leak for a day with all lane checks green.
