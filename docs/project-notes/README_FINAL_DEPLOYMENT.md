# Win's VPN Final Deployment

## Mandatory release order

This document is an execution runbook, not permission to deploy an unfinished
candidate. Production deployment, public downloads, store upload, portal
submission, and publication are prohibited until every earlier step below has
completed for the same release input index.

1. Run the final local release tests and obtain the Fable 5, GLM 5.3, and
   Daybreak Blue final reviews. Resolve every release-blocking finding.
2. Create the immutable source and dependency freeze, including the exact
   `RELEASE_INPUT_INDEX.json` that will bind every build and receipt.
3. Produce genuine, exact signed artifacts and receipts for every required
   upload target. Never substitute a draft, an old build, or a hand-authored
   receipt.
4. Run the isolated fresh three-VM GCP proof against the exact frozen client
   release. Reverify and retain its mode-0400 acceptance receipt as specified
   in [GCP proof fleet runbook](docs/runbooks/GCP_PROOF_FLEET.md).
5. Record and reverify cross-store readiness. Its final local record requires
   the current GCP acceptance receipt and rejects a receipt bound to a
   different release index.
6. Complete owner store readiness: console declarations, listings, privacy
   answers, screenshots, signing authority, and immutable upload receipts.
7. Only after steps 1 through 6 are verified may an authorized operator run
   any production deployment, store upload, public-download update, or
   publication action.

There is no production exception for a green local build, a draft store
listing, a planned GCP fleet, or a receipt from another release. The commands
below are for a separately authorized post-proof production rollout only.

Active deployment uses one installer per server role:

- `server/wins_control_plane_setup_ONETOUCH.sh`
- `server/wins_data_plane_setup_ONETOUCH.sh`
- `server/wins_core_server_setup_ONETOUCH.sh` for the optional physical Double VPN core

The old standalone edge-hardening script and duplicate root deployment drafts were removed; data-plane hardening is generated by the data-plane installer as `/usr/local/bin/wins-edge-hardening`.

Each installer supports a no-change installation preflight. Run `--preflight`
first on the freshly reset host, then run `--deploy`. This mode checks only
installation prerequisites; it does not validate an already deployed runtime.
The former `--validate` spelling remains a compatibility alias for
`--preflight`. A deployment writes
`/etc/winsvpn/role` before package changes so accidentally running the wrong
role on a configured host fails closed. For unattended production deployment,
generate `ADMIN_TOKEN` once outside Git and inject it through root-owned
mode-`600` `/root/winsvpn-secrets.env`. Use the same `ADMIN_TOKEN` on the hub,
every data plane, and the optional core. With the default hidden-origin design,
legacy SPA values are server-generated and unused; never compile an admin or
SPA secret into an app.

On the Windows deployment workstation, `tools/wins_deployment_preseed.ps1`
keeps the complete preseed in a current-user DPAPI-encrypted, owner-only file
outside the repository. `TestProviders` performs read-only Cloudflare,
SMTP2GO, PayPal OAuth/webhook/active-plan/hosted-product, and rclone checks
without printing values. `Deploy` stages LF-only role-scoped files, transfers no secret on a
command line, runs remote `--preflight` first, and runs `--deploy` only after
the preflight succeeds:

```powershell
pwsh -File tools/wins_deployment_preseed.ps1 -Action Status
pwsh -File tools/wins_deployment_preseed.ps1 -Action RefreshPayPalProducts
pwsh -File tools/wins_deployment_preseed.ps1 -Action SelfTest
pwsh -File tools/wins_deployment_preseed.ps1 -Action TestProviders
pwsh -File tools/wins_deployment_preseed.ps1 -Action TestArtifacts
pwsh -File tools/wins_deployment_preseed.ps1 -Action AuditWorktree
pwsh -File tools/wins_deployment_preseed.ps1 -Action AuditGitHistory
pwsh -File tools/wins_deployment_preseed.ps1 -Action Deploy -Role control -Target ubuntu@CONTROL_HOST -IdentityFile C:\secure\control-key
```

Use `-RoleDefaultsFile` for public per-node identity/hostname overrides. The
wrapper refreshes the control trusted administration `/32` immediately before
a hub deployment and sends only `ADMIN_TOKEN` to Core; provider/payment/backup
credentials never fan out to Core or data planes. `ImportLegacy` is a one-time
migration aid for this workstation, not a substitute for provider rotation:
any reused value remains compromised until revoked and replaced.

`AuditWorktree` exact-matches the active DPAPI credentials against every
tracked and untracked non-ignored source file without printing values.
`AuditGitHistory` additionally scans every local Git blob, including dangling
objects. The publish-ready gate requires both. Deleting or ignoring a file is
not remediation: rotate or revoke each matched provider credential first, then
use a coordinated history rewrite, expire old clones/artifacts, garbage-collect
local objects, and rerun the audit. The future fresh-install `ADMIN_TOKEN` can
be rotated safely with `-Action RotateAdminToken`; provider credentials require
provider-side replacement and cutover proof before their old values are
revoked.

## Control Plane

Run on a fresh Ubuntu 24.04 hub:

```bash
sudo -E bash server/wins_control_plane_setup_ONETOUCH.sh --preflight
sudo -E bash server/wins_control_plane_setup_ONETOUCH.sh --deploy
```

Before either command, install populated root-owned
`/root/winsvpn-defaults.env` and `/root/winsvpn-secrets.env` files. Production
`--preflight` checks the complete SMTP2GO, PayPal, Cloudflare Tunnel Read/Edit and DNS,
rclone, shared admin, and trusted-SSH-CIDR contract before package changes.
The existing public active-gateway Gist remains a read-only fallback for the
stable Cloudflare Tunnel hostname. Gist write automation is opt-in, so a fresh
hub does not need or retain a GitHub write token.
Never print the admin token or place it in an app build/public file.

The installers wait for cloud-init and active provider package jobs before they
touch APT. Their top-level and generated-maintenance environments set
`DEBIAN_FRONTEND=noninteractive`, `DEBIAN_PRIORITY=critical`,
`APT_LISTCHANGES_FRONTEND=none`, `NEEDRESTART_MODE=a`, and
`UCF_FORCE_CONFFOLD=1`. They keep existing provider configuration files
(`--force-confdef --force-confold`), wait up to 300 seconds for the dpkg lock,
retry repository acquisition three times, disable pseudo-TTY output, and use
`apt-get upgrade --with-new-pkgs` so packages are not removed unattended. Every
APT install/maintenance call uses the same retry wrapper. The deployment
validator also rejects early-exit `grep -q` pipelines because `set -o pipefail`
can otherwise turn an upstream SIGPIPE into a false installation failure. Set
`APT_ALLOW_REMOVALS=1` only for a supervised rebuild where you will review the
`full-upgrade` plan. YABS is disabled by default because a benchmark is not a
deployment dependency; `RUN_YABS=1` downloads a commit-pinned,
SHA-256-verified copy.

If Ubuntu creates `/var/run/reboot-required`, each role stops at a dedicated
boundary immediately after the package phase—before runtime secrets are
materialized or any public VPN listener is installed—and records the current
kernel boot ID in a root-only marker. The Windows `Deploy` wrapper treats exit
code 75 as this controlled boundary, reads the old boot ID, requests one
reboot, waits up to ten minutes for SSH to return with a different boot ID,
then repeats `--preflight` and resumes the idempotent `--deploy`. A second reboot
request fails closed for inspection instead of looping. Use
`-NoAutomaticReboot` when an operator must perform that reboot manually.

The control and data installers also install a weekly maintenance timer at
**4:00 AM every Sunday in each server's local timezone**. Maintenance uses the
same no-removal APT upgrade policy. Ubuntu's daily `unattended-upgrades` remains
installed for security patches. A separate daily randomized
`wins-suricata-update.timer` runs `suricata-update`, performs an explicit
`suricata -T` against the candidate configuration, and only then requests a live
ruleset reload through the Suricata command socket. It falls back to the
documented signal reload and starts the service only if it was already inactive;
a rejected update never replaces the running ruleset.

Control and data roles enable OISF's official `suricata-stable` PPA and require
Suricata 8.0.7 or newer. Ubuntu 24.04's older standalone `suricata-update`
package conflicts with the OISF Suricata 8 package, which already bundles that
tool. A rerun simulates the removal plan, permits removal only when the sole
package is `suricata-update`, then verifies the installed binary is owned by
`suricata`, meets the stable minimum, supports NFQUEUE, and accepts the generated
configuration. This migration deliberately happens before any general upgrade.
A disposable Ubuntu 24.04 WSL package rehearsal with stdin closed completed the
current package phase without a prompt, installed Suricata 8.0.6 from the OISF
stable PPA with NFQUEUE support, left `dpkg --audit` clean, and required no
reboot. WSL package-only tests may temporarily install
`tools/wsl_package_rehearsal_policy_rc.d` as `/usr/sbin/policy-rc.d` to prevent
Windows-owned port 22 from breaking the OpenSSH maintainer script; the runner
must remove it in a guaranteed cleanup path, and production hosts must never
install it.

Useful validation:

```bash
systemctl status wins-hub.service --no-pager -l
journalctl -u wins-hub.service -n 80 --no-pager
curl -sS http://127.0.0.1:8000/healthz
curl -sS http://127.0.0.1/nodes
wins-menu
```

The installer writes private runtime values to `/root/vpn_auth.env` and `/root/vpn_auth/.env` with mode `600`.
It accepts rclone configuration only from `RCLONE_CONFIG_SOURCE` or
`RCLONE_CONFIG_B64`, writes it mode `600`, verifies the named remote, and stops
the deployment when the required backup cannot be reached.

Hub SSH is key-only. Confirm an `authorized_keys` file exists, or inject one
complete public key with `HUB_SSH_PUBLIC_KEY`, and set current trusted CIDRs in
`HUB_ADMIN_SSH_CIDRS` before deployment. Restrict provider TCP 22 to those
trusted CIDRs. Cowrie is disabled on the hidden hub by default because a public
honeypot would reveal the protected origin; use a separate disposable decoy
VPS/IP for deception research. `HUB_SSH_PASSWORD_AUTH=1` and
`HUB_ALLOW_GLOBAL_SSH=1` are recovery-only overrides.

The control plane also installs Suricata IDS/IPS plus Fail2Ban by default.
Narrow inbound TCP 80/443 traffic enters NFQUEUE 0, where deterministic local
drop rules can block high-confidence attacks; ET Open remains alert/evidence
oriented to avoid turning noisy signatures into customer-impacting blocks.
The email monitor throttles notifications while retaining forensic events.
Fail2Ban inserts SSH bans into the owned
`WINVPN-HUB-INPUT` chain. Temporary bans stay live in Fail2Ban and are not
persisted into `/etc/iptables/rules.v4`. Useful checks:

```bash
systemctl status suricata fail2ban --no-pager -l
systemctl status wins-security-alert-monitor.timer --no-pager -l
systemctl status wins-weekly-maintenance.timer --no-pager -l
fail2ban-client status sshd
iptables -L WINVPN-HUB-INPUT --line-numbers -n -v
iptables -L f2b-sshd --line-numbers -n -v
tail -n 50 /var/log/suricata/fast.log
```

The generated Nginx API responses always carry HSTS, no-store, restrictive CSP,
nosniff, frame-deny, referrer, and permissions headers, including when the
Cloudflare tunnel reaches loopback over HTTP. `wins-gateway-canary` verifies
those headers through every public hub hostname and fails if Double VPN is ever
advertised with zero usable exits.

Security alerts are emailed to `security@winsvpn.com` through the rotated SMTP2GO credentials for P1 and P2 only (`SECURITY_ALERT_EMAIL_PRIORITIES=1,2`). P3 events are stored in the security event DB without email. Only loopback is exempt by default; configure any operator exemption dynamically with `SECURITY_ALERT_EXEMPT_IPS`. To test SMTP alerting after deploy:

```bash
/usr/local/bin/wins-security-alert-monitor --test-email
```

The monitor throttles repeated matching alerts for 300 seconds and caps each run at 20 emails by default (`SECURITY_ALERT_THROTTLE_SECONDS`, `SECURITY_ALERT_MAX_EMAILS_PER_RUN`). Alert emails use readable aligned labels and Eastern time (`SECURITY_ALERT_TIMEZONE=America/New_York`); UTC remains in the local database for correlation, not in the email body.

Security events are also stored for 180 days in a separate local database, `/var/lib/wins-security-alerts/security_events.db`, for drilldown without mixing intrusion telemetry into the VPN subscription database. Query it locally as root:

```bash
wins-security-events --days 7 --limit 100
wins-security-events --days 30 --priority 2 --event-type admin --json
```

SSH attempt policy is applied on both server roles: `MaxAuthTries 5` closes one SSH connection after five auth attempts, and Fail2Ban bans a source after ten failed SSH attempts within one hour.

Set `INSTALL_CONTROL_IDS_IPS=0` only for emergency troubleshooting. Data-plane
Suricata is enabled by default only for the public Xray TCP transports; raw
AmneziaWG UDP 9110 and customer exit traffic are deliberately excluded.

Use at least 4 GB RAM for the control hub. The previous 2 GB IONOS hub has a
confirmed OOM-killer event with the control stack; Suricata's generated caps
are bounded, but 2 GB is not an acceptable production floor. T-Pot is not
installed on the hub.

With `HIDE_CONTROL_ORIGIN=1`, provider ingress must not expose TCP
80/443/8000/8080 or UDP 9110/62201. Restrict TCP 22 to
`HUB_ADMIN_SSH_CIDRS`. The
Cloudflare tunnel is outbound, so it requires no inbound provider rule.

If an existing working hub must temporarily return to direct Nginx listeners
while a named tunnel credential is repaired, set `HIDE_CONTROL_ORIGIN=0` but
leave `CONTROL_DIRECT_CLOUDFLARE_ONLY=1`. Before changing any firewall rule,
the installer downloads and validates Cloudflare's official IPv4 origin ranges,
then permits 80/443 only from those sources; arbitrary Internet scans are
dropped without entering Suricata's queue. `CONTROL_LEGACY_SPA_UDP=0` keeps the
obsolete UDP 62201 recovery knock closed. This is a recovery posture, not a
replacement for the final outbound-only tunnel. See Cloudflare's
[authoritative IP range list](https://www.cloudflare.com/ips/) and
[tunnel firewall guidance](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/).

## Data Plane

Run on each fresh Ubuntu 24.04 exit node after the control hub is healthy.
Create root-owned mode-`600` defaults and secrets files containing node
identity, the hub IP/URL, the pre-generated shared `ADMIN_TOKEN`, and the
node's zone-scoped Cloudflare token, then validate and deploy:

```bash
sudo install -m 600 /dev/null /root/winsvpn-defaults.env
sudoedit /root/winsvpn-defaults.env
# Required public contents:
# HUB_DOMAIN=hub.winsvpn.org
# HUB_API_BASE=https://sync.winsvpn.org
# NODE_MANAGEMENT_TUNNEL_ENABLED=1
# Leave IONOS_HUB_IP and WINS_HUB_IP unset.
# Put ADMIN_TOKEN, Cloudflare DNS token, and management-tunnel credentials in
# /root/winsvpn-secrets.env.

sudo bash server/wins_data_plane_setup_ONETOUCH.sh --preflight
sudo bash server/wins_data_plane_setup_ONETOUCH.sh --deploy
```

The data-plane postflight does not report success until Nginx, Xray,
AmneziaWG, AdGuard Home, Fail2Ban, forwarding, IPv6 blocking, local DNS, hub
registration, and the hub management path all validate. The installer creates
the outbound tunnel and registration helper, proves management before closing
direct SSH, installs the provider firewall and key-only SSH policy, then proves
management again. Either failed proof aborts deployment. The default outbound
management tunnel deliberately prevents the control origin IP from being
stored on a data plane.

DNS is deterministic rather than fastest-response based. AdGuard Home applies
the official AdGuard DNS filter locally for every VPN client, sends allowed
queries to Quad9 over DoH, and uses Cisco OpenDNS over DoH only when Quad9 is
unavailable. Set `DNS4EU_COMMERCIAL_DOH_URL` in the root-owned secrets file to
add the authorized Whalebone/DNS4EU provider endpoint as a second fallback.
Never use the public `joindns4.eu` endpoints on a commercial Win's VPN data
plane; the installer rejects them because that service excludes commercial and
connectivity-provider traffic.

Optional overrides:

```bash
sudo NODE_SLUG=france NODE_NAME="France - Paris" NODE_FLAG="FR" NODE_HOST=france.winsvpn.org \
  STEALTH_HOST=france.app-cloud-sync.net WG_PORT=9110 STEALTH_TRANSPORTS=80:none,443:tls XRAY_PATH=/wins-stealth-tunnel \
  bash server/wins_data_plane_setup_ONETOUCH.sh
```

Client key generation does not add a separate data-plane setup command. Phones generate the client WireGuard/X25519 keypair, the control plane authenticates the account and stores only `client_public_key`, and the hub pushes that public key plus the optional preshared key to the selected data plane with `awg set awg0 peer ...`. The data plane uses container name `amnezia-awg2` and an immutable SHA-256 digest for the reviewed `amneziavpn/amneziawg-go` image. Update that digest only as a reviewed source change.

The ordered default stealth transports are public `80:none,443:tls`, while raw
AmneziaWG remains UDP `9110`. Nodes advertise the exact ordered list and apps
try only what was advertised, so either 80 or 443 can be the primary without a
hardcoded port assumption. The admin token is never sent over plaintext; data and core
roles reject `http://` hub URLs unless `ALLOW_INSECURE_HUB_HTTP=1` is explicitly
set for an isolated test network.

On a Data installer rerun, the existing node first withdraws its hub promotion
and live assignments, then engages the node-local serving latch before the
ordinary deployment body mutates the host. Both holds stay closed through
postflight. Completion releases the deployment holds but leaves the node
unpromoted, so routine registration or later healthy probes cannot reuse the
old promotion. Fresh frozen evidence and a new operator promotion are required.

Post-install validation:

```bash
iptables -S | grep WINVPN
iptables -t nat -S | grep WINVPN
iptables -t mangle -S | grep WINVPN
docker ps
systemctl status wins-edge-hardening.service --no-pager -l
systemctl status fail2ban --no-pager -l
systemctl status wins-weekly-maintenance.timer --no-pager -l
fail2ban-client status sshd
systemctl status wins-node-register.timer --no-pager -l
journalctl -u wins-node-register.service -n 80 --no-pager
/usr/local/bin/wins-node-register
```

## Optional Double VPN Core

The physical core is a separate role and is never installed on the control
hub. Its canonical disk contract is
`CORE_DISK_ENCRYPTION_MODE=auto|luks|substitute`: `auto` uses LUKS when the
root is already LUKS-backed and otherwise resolves to `substitute`; `luks`
refuses a plaintext root; and `substitute` enforces random-key encrypted swap,
the Core secret permission floor, and suppression of core dumps, persistent
journals, and hibernation. No posture permits plaintext active swap.

The substitute posture does not protect an offline disk or provider snapshot.
For that reason, `substitute` and `auto` on a plaintext root fail preflight
unless the root-owned role input contains this exact, case-sensitive,
whitespace-sensitive acceptance:

```bash
CORE_DISK_ENCRYPTION_SUBSTITUTE_ACCEPT=I_ACCEPT_OFFLINE_DISK_AND_SNAPSHOT_EXPOSURE
```

This value records explicit operator acceptance of the weaker boundary. It is
not proof of the identity or authority of the person who approved it, so retain
the separate owner authorization with the role inputs. LUKS hosts do not need
the value and do not downgrade when it is present. To require LUKS regardless
of detected state, set `CORE_DISK_ENCRYPTION_MODE=luks`. For an owner-approved
plaintext-root host, set `CORE_DISK_ENCRYPTION_MODE=substitute` and the exact
acceptance value above. Put the selected mode and any required acceptance in
`/root/winsvpn-defaults.env`, add the current hub token, confirm the router
forwards TCP 80 and UDP 9210 to the core host, then run:

```bash
sudo bash server/wins_core_server_setup_ONETOUCH.sh --preflight
sudo bash server/wins_core_server_setup_ONETOUCH.sh --deploy
sudo wins-core-diagnose
```

The core postflight validates Docker, AmneziaWG ingress, Xray, Nginx,
Fail2Ban, public-ingress firewall rules, forwarding, IPv6 blocking, local
stealth health, persisted keys, and a live assignment sync with the control
hub. A new Core registers dark. An upgraded Core first withdraws its hub
promotion and live assignments, then installs a local firewall hold before the
first ordinary host mutation. That hold and the hub deployment block remain in
place through postflight. Completion releases the deployment holds but does not
restore promotion. After fresh frozen Core gate evidence is complete,
run `sudo wins-admin` on the hub and choose option 22 to promote the configured
Core. Option 23 withdraws it immediately, clears runtime readiness, and
deactivates its live assignments. Routine registration preserves a promotion;
an installer rerun intentionally consumes it and requires a new generation.

Data-plane direct AmneziaWG remains UDP 9110; UDP 9210 is reserved for the
home/core first hop and is not a replacement for data-plane port 9110.
The generated data-plane and Core Nginx servers suppress version disclosure and
apply HSTS, no-store, restrictive CSP, nosniff, frame-deny, referrer, and
permissions headers to health, Xray, and rejection responses. Their health
locations use `default_type` so Nginx does not replace the inherited header set.

The sync agent refreshes public endpoints only when they are IP literals, so a
changing residential WAN IP is re-registered while a configured hostname is
preserved. Every sync removes stale `corexN` containers, interfaces, route
tables, client policy rules, and configs. The hub expires a core after three
minutes without registration and reports Double VPN available only when at
least one managed online exit also exists. Per-interface IPv6 disablement is
verified in addition to the global sysctl.

## Honeypot Isolation

Cowrie is not a production control-hub component. It remains available only as
an explicit lab compatibility lane, runs unprivileged with denied egress, and
is disabled by default. A meaningful public honeypot belongs on a separate,
disposable decoy VPS/IP with no VPN-role trust or route to the hidden origin.
Never put production credentials in a decoy filesystem or treat captured
commands and payloads as trusted. The T-Pot installer also remains a parked
isolated-lab option and is not part of the production topology. Its dedicated
helper accepts only a fresh Ubuntu 24.04 decoy with the documented resource
floor, installs missing Git/CA prerequisites without package prompts, and uses
the pinned upstream installer's supported unattended mode. A standalone Hive
requires an externally preseeded strong `HONEYPOT_WEB_USER` and
`HONEYPOT_WEB_PASSWORD`; neither value is logged or stored in this repository.

## Cloudflare

The hub API uses an outbound Cloudflare Tunnel; its public hostnames are proxied
CNAMEs to the tunnel UUID and do not disclose or connect to the IONOS origin IP.
Data-plane Xray/WebSocket hostnames use proxied A records to their node. Neither
mechanism proxies raw AmneziaWG UDP `9110`, so data-plane direct mode still uses
the node's raw IP or a DNS-only hostname.

Control DNS layout (created and verified by the installer):

```text
sync.winsvpn.org          CNAME <CONTROL_TUNNEL_UUID>.cfargotunnel.com  Proxied
sync.winsvpn.com          CNAME <CONTROL_TUNNEL_UUID>.cfargotunnel.com  Proxied
hub.winsvpn.org           CNAME <CONTROL_TUNNEL_UUID>.cfargotunnel.com  Proxied
```

`app-cloud-sync.net` is reserved for data-plane Xray stealth hostnames. It is
not a control-hub API domain. The installer removes the retired
`app-cloud-sync.net` and `sync.app-cloud-sync.net` hub records so a stale
cross-account route cannot expose or misdirect the control plane.

Keep the public website on the current Cloudflare Pages deployment. Do not add
an apex A record that conflicts with the Pages-managed apex CNAME/route;
Cloudflare rejects same-name CNAME plus A/AAAA combinations.

Referral share links are intentionally branded and do not expose the sync
gateway in the app. The hub returns `https://winsvpn.org/referral/<code>` as
the primary share link and `https://winsvpn.com/referral/<code>` as the backup.
The Cloudflare Pages Worker must preserve those branded routes while proxying
the referral request to the hub.

The control installer removes conflicting Worker custom-domain bindings before
upserting the tunnel CNAMEs for `sync.winsvpn.org` and `sync.winsvpn.com`.
Do not create competing manual A/AAAA records. Both aliases are part of the
compiled backup order and must pass the postflight checks before deployment is
accepted.

Data-plane records and strict-TLS origin certificates do not need to be added
manually. Data planes and Cores hold neither a Cloudflare credential nor the
fleet `ADMIN_TOKEN`: the hub is the only holder of the app-cloud-sync.net token
(`CLOUDFLARE_APPCLOUD_API_TOKEN`), and its edge broker performs each DNS,
Origin CA, ACME and redirect operation for an authenticated node or Core,
limited to the hostnames the operator assigned to it. Assignments and the
fail-closed reservation inventory (zone apex plus every live and retired hub
route) accept only the hub-only `EDGE_ADMIN_TOKEN`. A node installer that finds
a Cloudflare credential or `ADMIN_TOKEN` on the host refuses to run; it accepts
only its existing node token or a short-lived bootstrap grant. Admin-only
steps (custom hostname assignment, management tunnel minting, the grant) run
operator-side with `tools/wins_operator_prepare_subject.sh`, whose fragment the
preseed tool appends to that one target's role secrets
(`-SubjectSecretFragment`). Existing nodes migrate with
`server/wins_edge_credential_migrate.sh`. The data-plane installer asks the hub
for one proxied A record per node using the node slug, such as
`united-states-los-angeles.app-cloud-sync.net`. Production strict mode requests
a hostname-verified Cloudflare Origin CA certificate for every advertised TLS
hostname through the hub, and stops before advertising a node when a required
broker operation fails. A self-signed certificate is never used
for an advertised strict-TLS route. Disable automation only for a disposable
direct-node simulation.

For all data planes, keep `NODE_HOST` as the raw node IP for direct AmneziaWG
UDP and let the installer create the Cloudflare-proxied `STEALTH_HOST` for
Xray/WebSocket. The hub is reached only through its hostname and restricted
management tunnel:

```bash
HUB_API_BASE=https://sync.winsvpn.org \
NODE_MANAGEMENT_TUNNEL_ENABLED=1 \
sudo bash server/wins_data_plane_setup_ONETOUCH.sh --deploy
```

If you want a short custom stealth hostname for one node, add `CLOUDFLARE_STEALTH_RECORD=la1.app-cloud-sync.net`; otherwise the script uses `NODE_SLUG.app-cloud-sync.net`.

If a script prints a Cloudflare DNS upsert warning with `Authentication error`, the token is probably using account-level permissions such as `Account DNS Settings`, which do not grant DNS record access for a domain. Edit or recreate the token using a zone-scoped policy:

```text
Policy scope/resource: Specific zone
Zone: app-cloud-sync.net
Permissions:
  DNS: Read
  DNS: Edit
  Zone: Read
  SSL and Certificates: Edit
```

Create the same zone-scoped policy for `winsvpn.org` if the hub script manages
`hub.winsvpn.org`. Do not choose `Account DNS Settings`; it does not grant A/CNAME
record access. The `SSL and Certificates: Edit` permission is also required to
issue the Origin CA certificate that Cloudflare Full (strict) validates. The
secure preseed copies only the app-zone DNS/Origin credential and zone ID to the
physical core. When `CORE_STEALTH_HOST` is empty, the core derives
`<CORE_ID>.app-cloud-sync.net`, upserts exactly that proxied record, and then
requests its certificate; a custom hostname remains supported. Rerun
`--preflight` after replacing the token; production deploys now fail closed on
DNS/API denial, a missing zone, an invalid hostname, or an unverifiable origin
certificate.

Cloudflare dashboard settings:

- Network > WebSockets: `On`.
- SSL/TLS mode for hub tunnel hostnames is independent of a public origin
  listener; the tunnel connects to loopback. For data-plane TLS origins, use
  `Full (strict)` only with a trusted Cloudflare Origin or public certificate.

### Final-audit pin and main-branch freeze

Finish and commit every audit-target repair before starting the final audit.
Then stop all main-integrating lanes, require a clean operator checkout attached
to `main`, and create one immutable audit pin plus its external receipt:

```bash
set -euo pipefail
repo_root="$(git rev-parse --show-toplevel)"
receipt="$HOME/.xprize/lane-reports-20260830/deployment-audit-freeze-$(date -u +%Y%m%dT%H%M%SZ).json"
python3 "$repo_root/tools/deployment_audit_freeze.py" pin \
  --repo "$repo_root" --receipt "$receipt"
python3 "$repo_root/tools/deployment_audit_freeze.py" check \
  --repo "$repo_root" --receipt "$receipt" \
  --expected-sha "$(git -C "$repo_root" rev-parse HEAD)"
```

`pin` refuses a dirty or detached checkout, a non-`main` branch, an existing
freeze, unexpected hook bytes, or a conflicting `core.hooksPath`. It creates
`refs/winsvpn/deployment-audit-freeze` with compare-and-swap semantics, enables
the exact tracked `reference-transaction` hook, writes a new mode-0600 external
receipt containing the commit and tree, and rechecks the complete state. While
the ref exists, the hook rejects a local update of `refs/heads/main` away from
the pin. The freeze ref is shared by the repository's worktrees. Lanes may
prepare work only on separate branches; none may merge, commit, reset, or
otherwise advance `main` until an audit verdict lands.

The hook is local defense in depth, not a security boundary against a hostile
repository administrator. Git configuration overrides, direct repository
metadata edits, and remote-side updates can bypass a client hook. The normative
control is the recorded freeze ref and receipt, the no-main-update procedure,
the operator `check`, and an independent detached audit checkout.

Create that checkout from the pinned object, not from a moving branch, and
verify it against the external receipt:

```bash
audit_root="$(mktemp -d /tmp/winsvpn-deployment-audit.XXXXXXXX)"
git clone --no-local "$repo_root" "$audit_root/repo"
pinned_sha="$(git -C "$repo_root" rev-parse refs/winsvpn/deployment-audit-freeze)"
git -C "$audit_root/repo" checkout --detach "$pinned_sha"
python3 "$audit_root/repo/tools/deployment_audit_freeze.py" verify-receipt \
  --repo "$audit_root/repo" --receipt "$receipt"
```

The final report must contain exactly one anchored `VERDICT: DEPLOYMENT GO` or
`VERDICT: DEPLOYMENT NO-GO` line plus anchored `Audited commit:` and
`Audited tree:` lines for the pin. After preserving that report, release the
hold with:

```bash
python3 "$repo_root/tools/deployment_audit_freeze.py" release \
  --repo "$repo_root" --receipt "$receipt" \
  --verdict /absolute/path/to/final-audit-report.md
```

Release compare-and-swap deletes only the matching freeze ref and restores the
prior local hook setting. A GO permits the separately gated deployment flow. A
NO-GO permits the next repair cycle, but confers no deployment authority.

### Approved checkout bytes

Every deployment phase must start from the exact full commit approved by the
final audit. Export `WINSVPN_DEPLOYMENT_REPO` as the absolute operator checkout
root and `AUDIT_APPROVED_SHA` as that full commit ID, then run this gate
immediately before staging or executing any deployment file:

```bash
set -euo pipefail
: "${WINSVPN_DEPLOYMENT_REPO:?export the absolute operator checkout root}"
: "${AUDIT_APPROVED_SHA:?export the final-audit-approved full commit SHA}"
repo_root="$(cd -- "$WINSVPN_DEPLOYMENT_REPO" && pwd -P)"
cd "$repo_root"

/usr/bin/env \
  -u GIT_DIR -u GIT_WORK_TREE -u GIT_INDEX_FILE -u GIT_COMMON_DIR \
  -u GIT_OBJECT_DIRECTORY -u GIT_ALTERNATE_OBJECT_DIRECTORIES \
  GIT_NO_REPLACE_OBJECTS=1 \
  /usr/bin/git --no-replace-objects -C "$repo_root" show \
  "${AUDIT_APPROVED_SHA}:tools/verify_deployment_checkout.py" \
| /usr/bin/python3 -I -B -S - \
    --repo "$repo_root" --approved-sha "$AUDIT_APPROVED_SHA" \
    --allow-ignored-paths
```

The verifier itself comes from the approved object, not from mutable worktree
bytes. It refuses a different HEAD, staged or unstaged changes, untracked or
active Git operations, hidden `assume-unchanged` or `skip-worktree` entries,
submodules, type or executable-mode changes, and any regular-file or symlink
bytes that differ from the approved tree. `pipefail` makes a failed `git show`
fatal. The isolated interpreter prevents local Python startup files from
changing the verifier.

`--allow-ignored-paths` is the explicit operator-checkout exception. It does
not authenticate or read ignored bytes. It inventories their byte-exact path
names twice, refuses ignored VCS and Python startup/test-hook injection paths,
and stamps the allowed flag, entry count, bytecode count, and path-manifest
digest into the receipt alongside the commit, tree, tracked-path count, and
tracked tree-manifest digest. Separately declared ignored role-default or
credential inputs retain their own validators and are not covered by this
tracked-source receipt. Omit this flag in a fresh audit checkout to retain the
strict default, which refuses any ignored entry.

Any later checkout mutation invalidates the receipt. Never clean, reset, stash,
or switch a dirty operator checkout automatically. Stop, preserve the local
work, and rerun this gate from a separate clean checkout at the approved SHA.

### Fresh-host SSH trust and mandatory deployment order

Before using `tools/wins_deployment_preseed.ps1 -Action Deploy`, verify the
fresh VPS Ed25519 host fingerprint through the provider console and pin it in
the deploying workstation's OpenSSH `known_hosts`. The deploy wrapper uses
`StrictHostKeyChecking=yes` and intentionally refuses trust-on-first-use. A
host reimage changes the key; remove an old entry only after the replacement
fingerprint is confirmed out of band. This is the one security decision that
cannot be made safely from the same untrusted network connection.

Deploy in this order:

1. Control hub: validate/deploy, then prove the outbound Cloudflare tunnel,
   health route, management-bootstrap endpoint, backup, SMTP2GO, and PayPal
   integration.
2. Data plane: keep management tunneling enabled, use customer AWG UDP 9110,
   register every explicit ordered Xray `port:security` route, and prove direct
   plus every fallback route.
3. Physical Core: use first-hop AWG UDP 9210, register the current heartbeat,
   assign at least one healthy managed data-plane exit, and only then test
   Double VPN.
4. Run exact-artifact live tests on Android, Windows, Linux, macOS, and iOS.
5. Publish only after `tools/public_release_gate.ps1` passes.

Port does not imply transport security. `80:none` and `443:tls` are defaults,
not special cases; `443:none`, `80:tls`, and nonstandard ports work when they
are explicitly advertised and configured. Linux and Windows now reject
malformed native Xray fields and add SNI/certificate verification only for
routes whose security value is `tls`. Both platforms stop the old Xray process
before validating the replacement, so an invalid response cannot leave a stale
tunnel running. Linux cleans up before writing the new config; Windows removes
its credential-bearing temporary Xray JSON after startup. The native readiness
gate enforces these lifecycle contracts.

## Linux App

The Linux runner now includes a native `wins_vpn/tunnel` method-channel bridge in `linux/runner/linux_tunnel_backend.cc`. It writes the generated local AmneziaWG config under the user's data directory, starts the bundled Xray for Winn Protocol stealth configs, and uses an already-authorized passwordless `sudo` policy, interactive `pkexec`, or root to create/remove the Linux VPN interface. It probes passwordless sudo before PolicyKit so minimal WSLg-style sessions without an authentication agent work, but it never bypasses a dismissed PolicyKit prompt. The archive carries hash-verified AmneziaWG tools `v3.1.20260812` and a reproducibly built, statically linked `amneziawg-go` userspace engine from pinned commit `1b86b2ae0e493e7ea93f8c1a0f0cb6735b1551f1`. `awg-quick` uses a compatible host kernel module first for performance and automatically falls back to the bundled userspace engine when the module is unavailable. Xray resolves the dynamic public transport endpoint before the tunnel route is installed, then runs without root privileges as the locked `winsvpn-xray` system identity. The helper first brings AWG up, then installs a UID-scoped priority-1 main-table rule directly after Linux's immutable local-table rule. It applies AWG's own fwmark only to that UID, saves the connection mark on Xray flows, restores it before inbound reverse-path validation, verifies the marked public route does not select `winsvpn`, and only then launches Xray. That ordering accounts for `awg-quick` dynamically assigning its own priorities, preserves strict reverse-path filtering, and prevents recursive Xray routing without leaking unrelated traffic that happens to share a Cloudflare address. Every UID rule and packet-mark rule is removed on failure or disconnect. When the host kernel explicitly disables IPv6, Linux removes only IPv6 AllowedIPs before invoking `awg-quick`; there is no usable host IPv6 path to leak, while IPv4 must still pass the tunnel-bound probe. The runner starts with umask `0077` and migrates legacy key, config, activation, and PIN state to owner-only permissions. Interface presence alone never claims validated internet. The explicit probe verifies the route selected for a public address uses `winsvpn`, binds curl to that interface, and returns a separate `bound_to_tunnel` fact.

refusal sentinel, and `tools/run_release_workflows.ps1` is retired. They never
test, build, sign, verify, upload, or publish. Local tests and independently
captured target evidence are the release authority. Build and sign on the
controlled local release host, then retain the exact local evidence.

For a fresh Ubuntu/Debian, Fedora, or Arch x86-64 desktop, download both `wins-vpn-linux-x64.tar.gz` and its adjacent `wins-vpn-linux-x64.tar.gz.sigstore.json` bundle. Provision the reviewed exact Cosign `v3.1.3` binary at `/usr/local/bin/cosign` and the root-owned local public key at `/etc/winsvpn/release-signing/cosign.pub` (never `curl ... | sh`), then run the one-touch bootstrap directly against the still-compressed archive:

```bash
./install-winsvpn-linux.sh wins-vpn-linux-x64.tar.gz wins-vpn-linux-x64.tar.gz.sigstore.json
```

The bootstrap authenticates the *complete, unmodified* archive with offline `cosign verify-blob` against that fixed local trust anchor, safety-checks every tar member (rejecting absolute paths, `..` components, links, devices, FIFOs, and duplicate members) with a Python `tarfile` preflight, and only then extracts into a fresh root-owned `0700` stage and hands off to `install.sh` there with a clean environment. Do not extract the archive yourself and run `install.sh` directly -- it refuses to run anywhere except inside a stage this bootstrap created.

`install.sh` preserves existing Debian-family configuration files, installs the minimal GTK, PolicyKit, routing, DNS, nftables, iptables, libsecret, and GNOME Keyring dependencies in package-manager order, verifies every privileged bundled runtime by SHA-256 plus an exhaustive `release-manifest.sha256` covering every staged file (corruption/tampering detection layered on top of the cosign-verified archive bytes, not a substitute for them), and atomically installs a root-owned bundle under `/opt/wins-vpn`. GNOME Keyring provides the standard per-user Secret Service required by the Linux app; if that service is unavailable or locked, sensitive-state reads and writes fail closed instead of falling back to plaintext. It does not install or replace a kernel module. PolicyKit, passwordless `sudo -n`, or root remains necessary when the app creates or removes the VPN interface.

Destination/IP split tunneling is available through the shared UI on Android,
Windows, Linux, macOS, and iOS. Android enforces ordinary per-app exclusions.
Windows supports destination-based exclusions only. Linux uses launcher-scoped per-app bypass: after connecting, launch
the selected app from Win's VPN so systemd places it in the verified cgroup-v2
slice whose packets receive the AWG routing mark. Apps opened normally remain
inside the VPN. Apple limits per-app VPN to MDM-managed apps/profiles rather
than ordinary consumer App Store clients.

## PayPal

The one-touch control-plane installer writes the live PayPal REST client
ID/secret and webhook ID into `/root/vpn_auth.env`. By default it idempotently
creates or repairs the path-exact stable webhook only after hub/Tunnel health
succeeds, persists the returned ID, restarts the hub if the ID changed, and
verifies all provisioning event subscriptions. You can override the contract
before running the script:

```bash
PAYPAL_MODE=live
PAYPAL_CLIENT_ID=...
PAYPAL_CLIENT_SECRET=...
PAYPAL_WEBHOOK_ID=...
PAYPAL_WEBHOOK_AUTO_ENSURE=1
PAYPAL_WEBHOOK_URL=https://sync.winsvpn.org/webhook/paypal
```

Then run:

```bash
systemctl restart wins-hub.service
systemctl start wins-paypal-sync.service
journalctl -u wins-paypal-sync.service -n 80 --no-pager
```

The PayPal engine verifies webhook signatures, stores webhook event state in SQLite for idempotency, retries transient PayPal REST failures, and provisions a subscription only after the live PayPal object reports `ACTIVE`. `CHECKOUT.ORDER.APPROVED` is deliberately not a provisioning event. Lifetime access requires a completed capture/sale whose product marker, exact preseeded amount, and currency all match the current hosted PayPal button. Durable sale/capture references are stored for reconciliation. Partial refunds retain access; full refunds and payment reversals expire the account and remove its peers. A refunded subscription remains on a payment hold until a later completed sale clears it, so periodic status sync cannot silently re-enable refunded access.

`wins-admin` includes PayPal dead-letter listing and single-event retry tools that resync the subscription from PayPal instead of replaying stored webhook bodies. In production strict mode, OAuth, every active-plan contract, and both public hosted-product name/amount/currency contracts fail before host mutation; the webhook is verified or safely created/repaired after the stable HTTPS hub is healthy. Run `python tools/test_paypal_entitlement_contract.py` as a release gate. Account provisioning is never silently disabled.

The encrypted preseed carries these product contracts; do not hardcode the
values in source or infer entitlement from a buyer-controlled description:

```bash
PAYPAL_LIFETIME_SUPPORT_AMOUNT=...
PAYPAL_LIFETIME_NO_SUPPORT_AMOUNT=...
PAYPAL_LIFETIME_CURRENCY=...
```

Account-creating PayPal options are:

- `one_month`: recurring subscription, calendar +1 month validity.
- `one_year`: recurring subscription, calendar +1 year validity.
- `lifetime_support`: one-time Lifetime Access + Tech Support, calendar +10 years validity.
- `lifetime_no_support`: one-time Lifetime Access without tech support, calendar +10 years validity.

## Payment Click Tracking

Use hub redirect links anywhere you want click attribution before PayPal opens:

```text
https://sync.winsvpn.org/pay/one_month?src=website_winsvpn_org
https://sync.winsvpn.org/pay/one_year?src=website_winsvpn_org
https://sync.winsvpn.org/pay/lifetime_support?src=website_winsvpn_org
https://sync.winsvpn.org/pay/lifetime_no_support?src=website_winsvpn_org
https://sync.winsvpn.org/pay/donation?src=website_winsvpn_org
```

The Android app now uses the same redirect pattern with `src=app_android`, and the Windows desktop preview uses `src=app_windows`. The hub logs option/source counts with HMAC IP buckets and hashed user-agent/referrer values, then returns a normal `302` redirect to PayPal. View click totals:

```bash
TOKEN="$(awk -F= '/^ADMIN_TOKEN=/{print $2; exit}' /root/vpn_auth.env)"
curl -sS -H "x-admin-token: ${TOKEN}" "http://127.0.0.1:8000/admin/payment-clicks?days=30" | jq
```

## No-Log Posture

The hub runs Uvicorn with `--no-access-log`, hub/data-plane Nginx configs use `access_log off`, and data-plane Xray uses `"access": "none"`. Runtime logs avoid account numbers, device hashes, email addresses, subscription IDs, SPA source IPs, and VPN traffic metadata. Verify abuse protection uses HMAC rate-limit buckets in SQLite, not raw source IPs or raw account numbers. Account/device/payment state is still stored in SQLite for activation, device limits, subscription sync, and revocation.

## Backups / Rollback

Hub backup:

```bash
sudo /usr/local/bin/wins-hub-backup
```

Node backup:

```bash
sudo /usr/local/bin/wins-node-backup
```

The first hub/node backup is started automatically after a successful one-touch deployment, after the externally injected rclone config is installed and its remote is verified. If the later initial upload fails, deployment remains complete and the backup command leaves a local archive under `/tmp`.

No rclone credential is bundled in source. Strict preflight requires
`RCLONE_CONFIG_SOURCE` or `RCLONE_CONFIG_B64`, installs it root-only, and fails
before deployment when `GoogleDrive_secured:` cannot be reached. To replace it
later:

```bash
sudo wins-rclone-config < /path/to/rclone.conf
```

Before major changes, copy `/root/vpn_auth/vpn_users.db`, `/root/vpn_auth.env`, `/root/node.env`, `/etc/iptables/rules.v4`, `/etc/nginx`, and `/usr/local/etc/xray`.
