# Turn 2 Submission: solpro

1. **Steelman of peer podiums**

   Podium 1's strongest points were:

   - The topology-specific BDP table correctly shows why 1 MiB is appropriate for the current 32-stream test but becomes marginal at eight streams.
   - `SO_SNDBUF` must be requested before `connect()` so the socket is configured before TCP window scaling and the upload begins.
   - Direct TUN ingestion is feasible only after defining a promotion barrier and descriptor replacement protocol. A bootstrap descriptor cannot simply remain installed after `VpnService.Builder.establish()` returns a promoted descriptor.
   - Preserving `LocalSocket` for Stage D avoids changing Kotlin's established downlink write path.
   - The proposed `receiveBufferSize = 262144` handset addition should not be accepted. It is outside OI-1 and has no demonstrated benefit for an upload socket.

   Podium 2's strongest points were:

   - The observed 2.416 carrier packets per call cannot be equated with `toEngineRing` drain occupancy without phase-specific telemetry. Carrier counters may include upload data, download ACKs, control packets, and segmentation effects.
   - Explicit `SO_SNDBUF` is not the same as increasing TCP congestion window. It only prevents sender queue capacity from constraining `cwnd`, receiver window, or pacing.
   - Linux can clamp or internally double a requested socket buffer. The effective value must be read back or observed through `TCP_INFO` and `ss -tinm`.
   - Changes to `toEngineRing` can alter the return ACK path of a downlink TCP flow even though no downlink payload function is edited. That is a valid challenge to the claim of 100 percent behavioral freezing.
   - The 884 Mbps engine figure and 401 Mbps UI figure require synchronized byte and monotonic-time boundaries before either is used as causal evidence.

   Podium 2's eventual proposal to hardcode a 4 MiB gateway `SO_RCVBUF` contradicts its own stronger autotuning analysis. The fixed gateway buffer should not be adopted.

2. **Corrections to the Arbiter synthesis**

   Several conclusions are directionally sound, but three assertions need qualification.

   First, the window correspondence is evidence, not proof:

   \[
   W_{\text{stream}}=\frac{T \times RTT}{8N}
   \]

   For 32 streams and 65 ms RTT:

   | Aggregate throughput | Implied per-stream in-flight bytes |
   |---:|---:|
   | 366 Mbps | 92,929.69 |
   | 400 Mbps | 101,562.50 |
   | 401 Mbps | 101,816.41 |

   This correspondence makes a roughly 93 through 102 KB ceiling credible. It does not distinguish sender-buffer limitation from receiver-window limitation, congestion control, pacing, or another queue.

   Second, the 2.416 carrier ratio cannot result directly from the stated smooth-arrival timer model:

   \[
   t_{\text{packet at 1G}}=\frac{1373 \times 8}{10^9}
   =10.984\ \mu s
   \]

   \[
   t_{\text{packet at 400M}}=27.460\ \mu s
   \]

   Therefore, packets arriving in 250 microseconds are:

   \[
   250/10.984=22.760\ packets\ at\ 1\ Gbps
   \]

   \[
   250/27.460=9.104\ packets\ at\ 400\ Mbps
   \]

   A claim that the timer expires with only 2.4 packets does not follow from these rates. The 2.416 statistic is measured at another boundary or over a mixed traffic interval.

   Third, the Turn 1 record was not literally unanimous on OI-4. Podium 2 objected that transmit-side gating also carries TCP ACKs generated by downlink traffic. The code-scope freeze is supportable, but 100 percent behavioral preservation is not established.

3. **OI-1 review and vote**

   First-principles BDP:

   \[
   1,000,000,000/8=125,000,000\ bytes/s
   \]

   \[
   125,000,000 \times 0.065=8,125,000\ bytes
   \]

   \[
   8,125,000/1,048,576=7.7486\ MiB
   \]

   Per stream:

   \[
   8,125,000/32=253,906.25\ bytes
   \]

   \[
   253,906.25/1024=247.955\ KiB
   \]

   Nominal 1 MiB headroom:

   \[
   1,048,576/253,906.25=4.1298
   \]

   Nominal aggregate window ceiling:

   \[
   \frac{32 \times 1,048,576 \times 8}{0.065}
   =4.1298\ Gbps
   \]

   This is a nominal queue-capacity ceiling, not a prediction that TCP will achieve 4.13 Gbps. The effective sender buffer can be clamped, and `cwnd` or `rwnd` can remain smaller.

   Linux receive autotuning on the gateway should remain enabled. A listener-level `SO_RCVBUF` is inherited by accepted sockets and marks the receive allocation as user-locked on Linux. That can prevent dynamic growth.

   Vote: AGREE

   Falsifiable basis: after the client setting is applied, socket readback and `TCP_INFO` must show that aggregate bytes in flight can exceed 8,125,000 bytes without persistent receiver-window limitation. If it cannot, the nominal 4.13 ratio is not operationally realized.

4. **OI-2 review and vote**

   `SCM_RIGHTS` duplicates a descriptor reference. It does not inherently require Go to own downlink writes. A carefully designed system could make Go the sole TUN reader while Kotlin remains the writer.

   That architecture still requires all of the following:

   - Quiescing Kotlin TUN reads.
   - Draining already-read AF_UNIX frames.
   - An ordered uplink barrier.
   - Installing the promoted descriptor.
   - Acknowledging promotion before Kotlin permanently stops reading.
   - Repeating the procedure when fd 84 is replaced by fd 102.
   - Preventing simultaneous Kotlin and Go reads from the same TUN queue.

   Those mechanisms are not part of the Stage D patch. Deferral is therefore correct even though descriptor handover remains a sound Stage E direction.

   The immediate flush condition should be described precisely. `bufio.Reader.Buffered()` reports Go userspace buffering, not bytes still queued in the AF_UNIX kernel socket. The proposed code flushes before a potentially blocking refill when no complete header remains locally. It does not prove that the kernel socket is empty.

   Vote: AGREE

   Falsifiable basis: under an AF_UNIX test that sends fewer than 512 frames and then stops, every accepted frame must reach `toEngineRing` without waiting for another frame or connection closure.

5. **OI-3 review and vote**

   Threshold accumulation times are:

   | Threshold | 400 Mbps | 1 Gbps |
   |---:|---:|---:|
   | 16 packets | 439.36 us | 175.744 us |
   | 32 packets | 878.72 us | 351.488 us |

   Thus:

   - At 1 Gbps, a threshold of 16 is crossed before the 250 microsecond timer.
   - At 400 Mbps, the timer still expires first with approximately 9.1 packets.
   - A 50 microsecond timer would collect only 4.55 packets at 1 Gbps and 1.82 packets at 400 Mbps, so Podium 1's proposed timer reduction conflicts with the batching objective.
   - `oldCount == 0` must remain. Otherwise, a consumer asleep on an empty ring might never wake to arm its bounded parking interval.
   - Signaling only on the actual threshold crossing avoids repeated notifications while the ring remains above `lowWater`.

   Vote: AGREE

   Falsifiable basis: under a smooth 1 Gbps synthetic producer, threshold-triggered wakes should occur near 16 packets and before 250 microseconds. Under a smooth 400 Mbps producer, timer-triggered wakes should contain approximately nine packets, not 2.4.

6. **OI-4 review and vote**

   The named downlink payload components remain textually unchanged. However, the claim of 100 percent preservation is stronger than a source-file freeze.

   `toEngineRing` carries all handset-to-gateway IP packets, including TCP ACKs generated in response to downlink data. Consider a consumer already parked with one ACK queued. If a push adds 15 ACKs:

   - With `lowWater = 32`, the count reaches 16 and no threshold notification occurs.
   - With `lowWater = 16`, the count crosses the threshold and immediately notifies the consumer.

   That changes downlink ACK residence time and can change ACK clocking, congestion-window growth, and measured downlink throughput. The `flushInboundBatch` change can likewise release downlink ACKs earlier.

   Vote: DISAGREE: a reproducible one-plus-fifteen ACK queue test causes an immediate wake with `lowWater = 16` but not with `lowWater = 32`, proving that the downlink TCP feedback path is behaviorally changed even though the downlink payload functions are unedited.
