### Attack on RV-B Design (Mandate 1)

* **Content-Length Budget and Premature EOF**: The client advertises `Content-Length: 134217728` (128 MiB) per stream based on a static division of the 4 GiB budget across 32 streams. In an 8-second test at 358 Mbps, each stream transmits approximately 11.2 MB before the client reaches the window deadline and executes `socket.shutdownOutput()`. When the client closes its write half, the gateway's `io.Copy(io.Discard, body)` encounters `io.ErrUnexpectedEOF` from Go's `net/http` internal body reader because fewer bytes arrived than advertised in `Content-Length`. In `speedtest_ingest.go`, any non-nil error triggers `w.WriteHeader(http.StatusRequestEntityTooLarge)` with `{"error":"read capped","received_bytes":N}`. The byte count `received_bytes` is mathematically accurate and reflects actual kernel-acknowledged payload bytes, but the server emits HTTP 413. `MainActivity.kt` bypasses this by regex-parsing `received_bytes` directly from the raw socket stream while unconditionally recording `statusCodes.add(200)` without verifying HTTP status line validity. Conversely, if a single fast stream exceeds 128 MiB, `io.Copy` ceases reading at the Content-Length limit and responds with HTTP 200, causing subsequent client chunk writes to fail with broken pipe or connection reset.
* **Concurrency Semaphore Under 32-Stream Reuse**: The gateway enforces `speedtestMaxConcurrent = 64` via a buffered Go channel. A standard upload test from one phone immediately acquires 32 slots (50% of the total capacity). A second concurrent test, or an immediate re-test before the previous 32 client sockets fully drain, exhausts the channel. Because slot acquisition performs a blocking channel send `s.concurrent <- struct{}{}` without a select-default reject, the 65th incoming stream blocks inside the handler for up to `ReadTimeout` (120 seconds) rather than failing fast with HTTP 429 or HTTP 503. Additionally, download requests on `/speedtest/down` contend for the exact same 64-slot pool, allowing heavy download runs to starve upload measurements.
* **Stale Router Latch Retention**: When the VPN tunnel terminates, Kotlin executes `VpnTunnelService.latchedInnerRouterV4 = null` in its cleanup sequence. In contrast, `lib/main.dart` stores `_winn3IngestRouterV4` indefinitely because no disconnect listener resets the variable. If the user reconnects to a node operating on a different inner subnet (for example, 10.10.1.1 instead of 10.10.0.1) or to a legacy WireGuard node lacking a Winn v3 descriptor, Dart attempts download speedtests against the stale IP `10.10.0.1:8455`, causing requests to hang until timeout. For uploads, Dart passes the stale IP to Kotlin, where `router != VpnTunnelService.latchedInnerRouterV4` triggers refusal, falling back to third-party testing only after incurring avoidable latency.

### Carrier Ingress Bottleneck Analysis (Mandate 2)

* **Ranking of Ceiling Candidates**:
  1. **Gateway Demux Contention and ReadLoop Stall**: In `cmd/winn3-gateway/main.go`, a single goroutine executes scalar `ReadFromUDPAddrPort` for all incoming traffic. Inside `s.deliverSessionDatagram`, every datagram invokes `ps.pipe.DeliverWithRetry(buf, 20)`. If a session inbox fills, `DeliverWithRetry` loops 20 times, sleeping 25 microseconds on attempts 3 through 20 (up to 450 microseconds per full event). This sleep halts the entire gateway UDP read loop, preventing packet draining from the kernel socket buffer and inducing OS-level UDP receive drops (`RcvbufErrors`). At 358 Mbps (32,000 packets per second), scalar syscall overhead and lock contention on the single read loop establish the primary performance ceiling.
  2. **Carrier Pipe Inbox Drops**: `carrier.DefaultPipeDepth` defaults to 256 (or 512 when derived from `DefaultTokenWindow / 2`). At 1 Gbps, 256 frames of 1400 bytes represent 2.87 milliseconds of buffer. Micro-bursts from 32 parallel TCP streams easily saturate a 256-slot channel during minor driver scheduling delays. When the inbox fills, dropped frames cause immediate TCP window collapse across the 32 streams, capping throughput at 358 Mbps.
  3. **Single Per-Session Driver Loop**: One goroutine consumes the session inbox, decrypts frames sequentially, and performs scalar `write()` syscalls into the Linux TUN character device via `gatewayForwardDevice`. While user-space crypto overhead is manageable, serializing all TUN writes through a single thread limits packet throughput under heavy multi-stream load.
  4. **Client AF_UNIX Batching (256 frames)**: At 358 Mbps, 32,000 packets per second divided by 256 yields 125 AF_UNIX write batches per second. This generates minimal CPU overhead on Android and does not restrict line rate.
  5. **Client SO_SNDBUF (8 MiB)**: At 1 Gbps with a 20 millisecond round-trip time, the bandwidth-delay product is 2.5 MB. An 8 MiB socket buffer exceeds requirements by more than threefold and provides no bottleneck.

* **AF_UNIX Batch Scaling Assessment**: Scaling batch size from 256 to 512 at the AF_UNIX/TUN framing layer will not double ingress. 125 batch transfers per second is already negligible overhead. Doubling batch size to 512 only reduces transfers to ~63 per second, saving trivial CPU cycles while failing to address the gateway-side UDP read loop stalls or inbox drop rates. The throughput ceiling is bounded on the gateway ingress path, not client AF_UNIX IPC.
* **Cheapest Discriminating Measurement**: Query the gateway status document at `/status` (or execute `ss -u -a` and inspect `pst := ps.pipe.Stats()` via gateway metrics) immediately after an ingest upload run. If `pipe_recv_errors` increases, the 256/512 inbox is overflowing and dropping packets. If kernel `RcvbufErrors` climbs while `pipe_recv_errors` remains zero, the single `ReadFromUDPAddrPort` goroutine is overwhelmed by scalar syscalls.
* **Cheapest Code Change**: Increase `carrier.DefaultPipeDepth` to 4096 in `winn3/carrier/pipe.go` (or set `Depth: 4096` in `main.go:newSession`), and eliminate the 25-microsecond sleep inside `DeliverWithRetry`. If upload speed immediately climbs from 358 Mbps toward 800+ Mbps, queue saturation was the bottleneck.
