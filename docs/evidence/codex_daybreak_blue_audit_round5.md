## 1. Executive assessment

This audit confirmed two High severity defects, three Medium severity defects, one Low severity performance defect, and one Low severity test defect. No Critical vulnerability was confirmed.

The most serious product defect is in the Firefox browser extension. A failed WebRTC or network-prediction privacy write is converted into a successful return value. The controller then removes its fail-closed block and may report `protected`. WebRTC UDP can remain outside the browser proxy.

The live website contains a separate High severity payment-integrity defect. Paid-plan cryptocurrency selectors fall back to a static donation wallet modal when automated checkout is unavailable or has not finished loading. A transfer to that wallet has no generated order or invoice, so it cannot drive automatic account provisioning. The live handlers were byte-for-byte identical to the workspace handlers at the time of the audit. The configuration endpoint was healthy, but a slow first load still exposes the race.

The control plane calls the external Smart Router before proving a paid caller owns the account or device. A party that knows an active account number can induce bounded external requests and latency before its bad credential is rejected. Existing rate limits reduce the scale but do not remove the ordering defect.

The live Content Security Policy allows the two site-owned inline scripts, but Cloudflare injects a fresh inline JavaScript Detection script whose hash changes per response. The fixed-hash policy rejects that script. The main site script is not blocked. Cloudflare's bot signal is the affected component.

Android holds a low-latency Wi-Fi lock for the whole tunnel lifetime. Android documents lower battery life, potentially lower throughput, and poorer roaming as tradeoffs of this mode. A VPN does not need to force real-time gaming latency policy throughout idle sessions.

### EXT-01: Firefox privacy enforcement fails open

**Evidence.** `extension/src/adapters/firefox.js:341-360` catches both privacy-setting failures and returns `not_applied`. It does not reject. `extension/src/background/controller.js:668-684` removes block rules whenever `applyPrivacyProtections()` resolves. It inspects neither returned state. The Chromium adapter has the correct behavior at `extension/src/adapters/chromium.js:438-471`: it verifies both the value and `levelOfControl`, then throws on failure.

An isolated controller reproduction returned this state after simulated Firefox write failures:

```json
{"state":"protected","privacy":{"webrtc":"not_applied","prediction":"not_applied"},"failClosed":false}
```

Mozilla documents that `BrowserSetting.set()` can resolve without taking control, and that the caller must inspect `levelOfControl`. Mozilla also documents `disable_non_proxied_udp` as the WebRTC setting that prevents non-proxied UDP. See [Mozilla privacy.network](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/privacy/network) and [Mozilla BrowserSetting.set](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/types/BrowserSetting/set).

**Root cause.** The Firefox adapter treats enforcement results as telemetry. The controller treats promise resolution as enforcement success. Those contracts disagree.

**Impact.** A browser or competing extension can refuse the write while WinsVPN removes its blocking rules and derives a protected state. HTTP may use the proxy while WebRTC sends UDP outside it, exposing a direct network address and bypassing expected VPN routing.

**Exact replacement.** Replace `FirefoxAdapter.applyPrivacyProtections()` with this complete method:

```javascript
  async applyPrivacyProtections() {
    const webRTC = api.privacy.network.webRTCIPHandlingPolicy;
    const webRTCChanged = await webRTC.set({
      value: 'disable_non_proxied_udp',
    });
    const webRTCState = await webRTC.get({});
    if (
      webRTCChanged !== true ||
      webRTCState?.value !== 'disable_non_proxied_udp' ||
      webRTCState?.levelOfControl !== 'controlled_by_this_extension'
    ) {
      throw new Error('Firefox WebRTC protection did not take effect');
    }

    const prediction = api.privacy.network.networkPredictionEnabled;
    const predictionChanged = await prediction.set({ value: false });
    const predictionState = await prediction.get({});
    if (
      predictionChanged !== true ||
      predictionState?.value !== false ||
      predictionState?.levelOfControl !== 'controlled_by_this_extension'
    ) {
      throw new Error('Firefox network prediction remained enabled');
    }

    return { webrtc: 'applied', prediction: 'applied' };
  }
```

**Verification.** Add negative tests in which each `set()` rejects, returns `false`, returns the wrong value, and returns `controlled_by_other_extensions`. For every case, assert that the controller installs blocking rules, reports an enforcement error, and never derives `protected`.

### SRV-01: Smart Router runs before caller authentication

**Evidence.** `_verify_account_sync()` validates account existence and business state at `server/wins_control_plane_setup_ONETOUCH.sh:19723-19769`. For automatic paid routing, it calls `smart_router_recommend_node()` at lines 19813-19821. Paid caller authorization does not occur until `require_verify_authorization()` at lines 19888-19914. The Smart Router performs an authenticated external HTTPS request with bounded time and response size, but the caller causing it has not supplied a valid device bearer token or activation secret yet.

The read-only rate-limit precheck at lines 8910-8929 rejects an already exhausted bucket. A failed credential consumes its budget only after the Smart Router returns. The existing limits constrain repeated abuse but still allow the permitted failure budget to generate external work.

**Root cause.** The code correctly moved advisory network work outside `BEGIN IMMEDIATE`, avoiding a long SQLite writer lock. It moved the work too early, across the authentication boundary.

**Impact.** Knowledge of an active paid account number is enough to induce Smart Router traffic and add up to its bounded network latency to each failed attempt. This is request and cost amplification, not an account or tunnel authorization bypass. The outbound payload reviewed here contains routing and capability data, not the account number, device ID, endpoint, or key material.

    requested_client_public_key: str,
    request: Request,

            SELECT device_auth_token_hash
              FROM devices
             WHERE account_number = ? AND client_public_key = ?

        return False

        SELECT activation_secret_hash,
               activation_secret_expires_at,
               activation_secret_used_at

### WEB-02: Cloudflare JavaScript Detection conflicts with fixed-hash CSP

**Evidence.** The live root response returned HTTP 200 with HSTS, `X-Frame-Options: DENY`, `nosniff`, COOP, CORP, a restrictive Permissions Policy, and the fixed-hash CSP defined at `web/_worker.js:1755-1756`. Three repeated GET responses each contained the two allowed site-owned inline scripts plus a 921-byte Cloudflare challenge script. The Cloudflare script hash differed on every response and none of those hashes appeared in the CSP. The two site-owned scripts matched their allowed hashes on all three responses.

Cloudflare documents this exact behavior. When JavaScript Detections is enabled and CSP has no nonce, the injected inline script can be refused. Cloudflare recommends a nonce and states that it adds the nonce to injected scripts after parsing the response CSP. See [Cloudflare JavaScript Detections](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/javascript-detections/).

**Root cause.** The worker uses immutable hashes for site-owned inline scripts. Cloudflare mutates the HTML later with a per-response inline script. A fixed hash cannot authorize changing bytes.

**Impact.** Cloudflare's JavaScript Detection signal does not execute reliably. Any WAF or bot-scoring policy that expects that signal can misclassify traffic. ## 6. Performance assessment

The protocol code has meaningful bounds. IPC request and response sizes are capped. Pipe writes have deadlines. MTU planning is carrier-aware and rejects values outside explicit ranges. Packet parsers check buffer lengths. Go framing, replay, and classifier fuzz targets sustained millions of inputs without a crash. Linux and Windows process supervision is bounded.

Three optimization gates remain before performance claims are supportable:

1. Apply and benchmark APPLE-01 receive-window caps. Measure the full appex, not a Go component in isolation.
2. Apply and benchmark AND-01 on a phone across idle, interactive, bulk-transfer, and roaming workloads.
3. Run identical packet-size and loss profiles on x86_64 and arm64 for Windows, Linux, macOS, Android, and iOS. Record CPU, peak resident memory, battery energy, throughput, p50 and p99 latency, reconnect time, packet loss, and system termination logs.

No claim of 2.5 Gbps, 15 MB Apple compliance, battery improvement, or cross-platform parity is established by this audit.
