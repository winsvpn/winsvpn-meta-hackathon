### DB-01: paid crypto plan can be misrouted into the donation flow

Severity: **High**
Affected service: live `https://winsvpn.org`
Root cause: two different cryptocurrency flows share the same coin-selector UI. The automated paid flow creates a plan-bound Monero order or BTCPay invoice. The static modal only displays donation receiving data. The deployed handler treats failure to find an automated button as permission to call `openModal(coin, planTitle)`.

Verified live evidence at 2026-09-14T07:41:26Z:

- `GET /api/site/crypto-config` returned HTTP 200 and advertised both automated paths as enabled.
- The live page's `setupCryptoPayments()` returns silently when configuration fetch fails and hides failed rows.
- The deployed coin handler at the live response's lines 6730 to 6759 calls `openModal(coin, planTitle)` when no automated control was triggered.
- A real Edge click on the 1 Month `Pay with Crypto` button collapsed the choices, and a second click reopened Bitcoin, Dash, Monero, and the two automated checkout buttons. Therefore the reported top-level button failure was not reproducible in this desktop Edge session.
- I did not click a coin because that could create an order. The failure branch is proven by deployed source and does not require a state-changing request.

Impact: during configuration failure, slow initialization, render failure, or a fast user click, paid-plan intent is converted into donation intent. A user can send funds believing a plan will be provisioned, but the static address has no plan, price, email, order ID, or settlement callback binding. Support must reconcile the payment manually, if it can be identified at all.

### DB-04: Cloudflare JavaScript Detection injection conflicts with CSP

Severity: **Medium**
Affected service: live website bot detection and browser console
Root cause: Cloudflare transforms the HTML response and appends a per-request inline bootstrap for `/cdn-cgi/challenge-platform/scripts/jsd/main.js`. The strict CSP contains hashes for the two application inline scripts but not the newly injected bootstrap. Its content changes per request, so a static hash is not stable. The live `Cache-Control` lacks `no-transform`.

Verified at 2026-09-14T07:41Z:

- The application JSON and main inline script hashes were present in CSP.
- The injected 921-byte script had a calculated SHA-256 token absent from CSP.

```text

```

Set it on every HTML response path, both Pages `_headers` and Worker responses. Do not add the observed injected script hash because it is request-specific. ## Performance and memory assessment

The current working tree contains a material packet-path improvement, but DB-02 prevents treating it as release evidence.

Measured on Apple M5 Max, Darwin ARM64, three runs:

| Benchmark | Range | Allocation result |
|---|---:|---:|
| 64-byte seal and open round trip | 653.7 to 675.0 ns/op, 94.82 to 97.90 MB/s | 0 B/op, 0 allocs/op |

| Original demux comparator | 226.0 to 233.9 ns/op | 536 B/op, 8 allocs/op |

Assessment:

- Cached demux is about 2.9 times faster than the comparator and removes eight allocations per packet lookup.
- The new `SealInto` and `OpenInto` call sites reuse buffers, removing packet-storage allocation from the measured core round trip.
- UDP carrier code raises send and receive socket buffers and contains kernel-option tests.
- Path MTU planning is centralized at 1450, negotiates the narrower endpoint, and derives inner MTU by carrier overhead. The conformance package passed.
- iOS receive windows and the 15 MiB watchdog bound memory, but physical throughput and jetsam behavior remain unverified.
- Android removed the full-session Wi-Fi performance lock and uses a bounded startup wake lock, improving battery posture.

Do not publish these performance figures as a shipped release result until the source and test files are tracked, a fresh clone repeats them, and target-device throughput is measured. Desktop microbenchmarks do not prove battery, kernel-copy cost, radio wakeups, VPN extension memory, or end-to-end encrypted throughput.

Recommended next measurements after custody is fixed:

1. Run 30-minute bidirectional UDP and TCP traffic at 64, 512, 1,200, and near-MTU payloads on every target architecture.
2. Record process RSS, iOS physical footprint, packet loss, retransmission, CPU time, context switches, FD or handle count, and energy impact.
3. Inject path MTU changes, suspend and resume, gateway rotation, and 1 percent, 5 percent, and 20 percent loss.
4. Compare current buffers against kernel-granted sizes. Treat `SetReadBuffer` requests as requests, not proof of granted capacity.
