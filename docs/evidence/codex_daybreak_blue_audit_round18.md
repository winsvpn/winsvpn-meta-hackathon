### DB-01: Winn v3 dual-auth verdict data race

Severity: **High**  
Area: Winn Protocol v3, Go session state  
Files: `winn_protocol_experimental/winn3/session/driver.go:557-566`, `driver.go:2107-2116`

#### Root cause

`DualAuthVerified()` directly reads `d.dualDone`. Successful dual-signature verification writes `d.dualDone = true` while the driver state machine holds `d.mu`. Other accessors, including `State()`, acquire the same mutex. The dual-auth accessor omitted it.

The race was reproduced by adding a temporary diagnostic test in the same package, repeatedly reading the accessor while another goroutine wrote under `d.mu`, and running:

```text
go test -race ./winn3/session -run TestCodexAuditDualAuthVerifiedRace -count=1
```

Expected secure result: PASS and no race report. Actual result: FAIL with a race report naming the read at `driver.go:561` and the write under the driver mutex. The temporary diagnostic file was removed after reproduction. A later full `go test -race ./...` passed because the permanent suite does not call this accessor concurrently with attestation completion. That broad pass does not invalidate the hostile result.

Callers include the Winn probe and canary status paths. A stale or racy security verdict can misreport whether the peer's dual signature was verified. Go defines a data race as invalid concurrent access; architecture-specific observation cannot make it safe.

#### Exact production fix

```diff
diff --git a/winn_protocol_experimental/winn3/session/driver.go b/winn_protocol_experimental/winn3/session/driver.go
--- a/winn_protocol_experimental/winn3/session/driver.go
+++ b/winn_protocol_experimental/winn3/session/driver.go
@@
-func (d *Driver) DualAuthVerified() bool { return d.dualDone }
+func (d *Driver) DualAuthVerified() bool {
+	d.mu.Lock()
+	defer d.mu.Unlock()
+	return d.dualDone
+}
```

Add this complete regression file as `winn_protocol_experimental/winn3/session/dualauth_accessor_race_test.go`:

```go
package session

import (
	"runtime"
	"sync"
	"testing"
)

func TestDualAuthVerifiedSynchronizesWithVerification(t *testing.T) {
	var driver Driver
	const iterations = 10000
	const readerCount = 8

	start := make(chan struct{})
	var wait sync.WaitGroup
	wait.Add(readerCount + 1)

	for reader := 0; reader < readerCount; reader++ {
		go func() {
			defer wait.Done()
			<-start
			for index := 0; index < iterations; index++ {
				_ = driver.DualAuthVerified()
				runtime.Gosched()
			}
		}()
	}

	go func() {
		defer wait.Done()
		<-start
		for index := 0; index < iterations; index++ {
			driver.mu.Lock()
			driver.dualDone = index%2 == 0
			driver.mu.Unlock()
			runtime.Gosched()
		}
		driver.mu.Lock()
		driver.dualDone = true
		driver.mu.Unlock()
	}()

	close(start)
	wait.Wait()
	if !driver.DualAuthVerified() {
		t.Fatal("dual-auth result did not retain the final verified state")
	}
}
```

### DB-05: Android lacks the Winn v1 Xray fallback leg

Severity: **Medium capability gap**  
Area: Android, Winn Protocol v1

The shared dispatcher implements generation-bound, single-use Winn v1 selection with AmneziaWG first and Xray as the next leg (`lib/winn_protocol_dispatch.dart:2010-2320`). Android deliberately reports `supports_xray = false`. Its service fails closed before DNS lookup, process launch, or performance locks if an Xray-dependent profile reaches it. This is secure behavior and prevents a silent downgrade, but it does not satisfy the requested Android behavior of trying Xray/VLESS-WS after an AWG handshake failure.

This cannot be corrected by enabling the flag. Android has no audited Xray producer, lifecycle owner, native payload custody, or socket-protection path in this snapshot. Setting the capability to true would convert a safe refusal into a false capability claim.

Required production work is a separately reviewed Android Xray transport with all of these acceptance properties:

1. A pinned, provenance-verified arm64-v8a and x86_64 payload.
2. VpnService-owned process lifetime and teardown on every generation change.
3. `protect()` on every outbound socket before any carrier packet is sent.
4. Loopback-only local ingress, authenticated configuration, and no shell command construction.
5. A generation-bound transition that is reachable only after the AWG handshake failure verdict.
6. Phone and TV device tests proving fallback, teardown, DNS behavior, and no traffic escape.

Until that producer exists, retain `supports_xray = false` and document Android Winn v1 as AWG-only. There is no safe one-line code change.

### DB-09: distributed edge rate limiting is external and unverified

Severity: **Medium if the zone-level rule is absent**  
Area: Cloudflare Pages, payment creation, translation, AI chat  
Files: `web/_worker.js:8-40`, `web/_worker.js:242-299`, `web/wrangler.jsonc:1-110`

The live Pages implementation falls back to an isolate-local JavaScript Map. The source states that this counter resets or varies by isolate and region. The repository says a zone-level WAF rate-limiting rule is the live cross-isolate control, but dashboard state was not available to this audit.

Impact is conditional. If the WAF rule exists and is enabled, the source limitation is covered at the edge. If it is absent, clients can distribute requests across isolates or regions and exceed the intended per-IP payment-order, translation, and AI limits. That can create provider load, API cost, and order spam. The hub still validates requests and payment authority, so this is not a demonstrated account-provisioning bypass.

Cloudflare documents zone-level rules as the supported way to count matching requests by IP across its edge and apply a 429 or block action: [Cloudflare rate-limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/) and [dashboard configuration](https://developers.cloudflare.com/waf/rate-limiting-rules/create-zone-dashboard/).

#### Exact edge configuration

Create a zone-level rate-limiting rule with this expression:

```text
http.request.uri.path in {"/api/site/ai-chat" "/pay/wallet/create-order" "/pay/wallet/capture" "/pay/monero/create-order" "/pay/crypto/create-invoice"}
```

Use IP as the counting characteristic, 20 requests per 60 seconds, Block as the action, 429 as the response status, and 60 seconds as the mitigation timeout. Create a second rule for translation:

```text
http.request.uri.path eq "/api/site/translate"
```

Use IP, 30 requests per 60 seconds, Block, status 429, and a 60-second mitigation timeout. Keep the Worker limiter as a local backstop. Do not publish `web/wrangler.jsonc` with its documented dummy namespaces.

Verification must be done with an authorized staging hostname. Send 21 payment-path requests and confirm request 21 returns 429 even when requests reach different edge locations. Send 31 translation requests and confirm request 31 returns 429. Confirm the dashboard event log names the intended rule and source IP. This audit did not perform that load or query private dashboard state.
