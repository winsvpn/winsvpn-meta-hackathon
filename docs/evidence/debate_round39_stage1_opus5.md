# Round 39 stage1: claude-opus5

## VERDICT

**Part 1:** CONDITIONAL PASS. The design is coherent and the live numbers are self-consistent, but two items must be confirmed in code before this ships beyond Canada, and one design ratio (client batch 256 against gateway inbox 256) is actively harmful if scaled the way the mandate proposes.

**Part 2:** REJECT the framing as stated. "The 3.3x asymmetry is INSIDE Winn v3" does not follow from the evidence in this packet. The ingest tool isolates *directions*, not *layers*. Ranking gateway internals before excluding the client's access uplink risks a deploy cycle spent on the wrong stage.

## PART 1: IMPLEMENTATION FINDINGS

**F1, bind scope vs chain scope (high, blocking).** The probe-resistance claim "untouched" holds only if 8455 is unreachable from the public IP. Two independent conditions carry it: the listener binding `assign.V4` rather than a wildcard, and `WINN3GW-INPUT` being entered from `INPUT` for all interfaces rather than scoped to `winn3gw0`. If the jump is interface-scoped and the main INPUT policy is permissive, a wildcard bind (a `net.JoinHostPort` with an empty host is the usual way this happens) puts an unauthenticated, fingerprintable JSON responder and a 1 GiB zero-generator on the public address. That is a distinctive active-probe signature, which is exactly the property the cover listener exists to protect. (UNVERIFIED-LIVE: the actual bind string and the jump rule's interface match.)

**F2, latch site moved out from under verification (high, blocking).** The fix relocated the latch from the MTU block to the staged-start path, immediately after `WinnV3SessionPlan.from`. The native raw-socket gate's entire value is that the latched dotted-quad came from a signed descriptor. Relocating the latch to a parse site rather than a verification site means the ordering guarantee now rests on whatever calls `WinnV3SessionPlan.from`. If any path can reach staged-start with a `[winn]` section that has not passed `verifyWinn3Descriptor`, the gate degrades to "accepts whatever the config says" and the cleartext-policy bypass becomes an arbitrary-host primitive. (UNVERIFIED-LIVE: whether every caller of the staged-start path is downstream of descriptor verification.) Secondary: the gate pins the address but the packet does not mention pinning the port or the byte budget. Pin both.

**F3, truncated-body accounting. CONFIRMED, with a caveat.** The arithmetic makes truncation the normal case, not the edge case: 8 s at 1 Gbps aggregate is ~1 GB total, ~31 MB per stream against a declared 128 MiB budget. Every stream ends mid-body on every run. `io.Copy` returns bytes-copied plus the error, so a handler that discards the error still answers with a correct count, and the observed 32x HTTP 200 with 358 MB accounted proves that path works. Half-close is also fine: `shutdownOutput` sends FIN, the server reads clean EOF at the body reader, and writes the response back over the still-open reverse direction. Two residual defects:

- **Error class is invisible to the client.** A normal window-end abort and a `MaxBytesReader` trip both surface as a count. The second one is a truncated measurement (client kept sending, server stopped counting at 1 GiB) and the connection close may eat the response entirely, silently zeroing that stream. Unreachable below ~8 Gbps aggregate, so latent, but add a `"truncated":bool` field now while it costs one line.
- **Declared Content-Length is fiction.** If the client declares 128 MiB per stream, every request looks like a protocol violation to any middlebox or future proxy. Chunked encoding with a terminating zero-chunk at window end gives the same result with a clean protocol story.

**F4, semaphore 64 and the elapsed_ms origin (medium).** Sixty-four slots serves exactly two concurrent 32-stream testers. A third client either blocks or gets rejected, and in both cases the *other* tester's number is corrupted, not just the newcomer's. The 2-slot anecdote is the proof this matters. More precisely: if `elapsed_ms` starts before the semaphore acquire, queued time inflates the denominator and deflates the rate, which is the most likely mechanical explanation for how a 2-slot deploy read 242 rather than something near the 2-stream line rate. Two fixes: start the timer after admission, and have the client compute `sum(received_bytes) / client_wall_window` rather than trusting per-stream elapsed (32 streams do not start simultaneously).

**F5, hardcoded port 8455 and the DROP stall (medium).** The gateway takes the port as a flag; the Dart target hardcodes it. On Canada the fallback cost "one refused request" because the probe reached a closed or open port and got an RST. On any node with the chain's terminal DROP and no rule 6, that same probe gets silence and the client waits out a full TCP connect timeout before falling back. That stalls the whole test, not one stream. Carry `speedtest_ingest_port` in the signed descriptor, treat absence as "skip the primary target", and put a hard 1500 ms connect timeout on the probe regardless.

**F6, stale Dart target after reconnect (medium, latent).** The native latch clears at teardown and the Dart field does not, so a reconnect to a different node leaves the Dart target pointing at node A's inner address. The upload leg fails safely (the gate compares against node B's latch and refuses, fallback engages). The download leg does not go through the gate: it is a plain cleartext GET to an RFC1918 address, and if the route does not cover it, that request leaves the tunnel toward whatever sits at that address on the user's LAN. Today this is almost certainly masked, because rule 6 suggests every node uses `10.10.0.0/24` with `.1` as the inner router (UNVERIFIED-LIVE: whether inner subnets are per-node unique). Uniform addressing also means the gate's equality check currently accepts the same constant everywhere, so it is buying less than it appears to. Clear the Dart field in the same teardown handler, and build the target only when the current session has a verified descriptor.

**F7, no per-peer budget (low to moderate, depends on transit billing).** Any address in `10.10.0.0/24` can hold all 64 slots and pull 1 GiB per request. There is no amplification (the client must receive what it requests), so the ceiling is denial of the measurement service to other clients plus metered egress burn. A per-source concurrent cap of 32 and a bytes-per-minute budget closes it.

**F8, WriteTimeout 120s sets a throughput floor (low).** The 50 MiB Dart target needs ~3.5 Mbps sustained or the server cuts the response; the 256 MiB default needs ~17.9 Mbps. Fine for the intended use, wrong for a diagnostic tool pointed at a degraded link, which is precisely when you most want the number.

**F9, slow start inside the window (low).** Thirty-two streams reaching steady state across a tunnel takes on the order of 10 to 15 RTTs. At ~60 ms that is roughly one second of an eight second window (UNVERIFIED-LIVE: tunnel RTT to the Canada node). The reported 358 likely understates steady-state ingress by 5 to 10 percent. Report a peak 1 s sub-window alongside the mean.

**Arithmetic rechecked from first principles.** 358 MB in 8 s = 44.75 MB/s = 358 Mbps (the numeric coincidence is real, it holds exactly at an 8 s window). 32 x 128 MiB = 4 GiB, matching the stated budget, and 128 MiB sits under the 1 GiB per-request cap. 1 Gbps x 8 s = 1 GB. Go's `flag` package does stop at the first non-flag argument, so a stray bare token in ExecStart silently discarding every later flag is the correct explanation for the phantom `-peer-registry missing`. All consistent.

## PART 2: INGRESS CEILING

**The confound that outranks the whole ranking.** 1166 down against 358 up on a phone is the signature shape of a consumer access link or a single-radio Wi-Fi client, where uplink airtime is shared with downlink ACKs and the ratio lands in exactly this range. The packet also calls the download "pure tunnel, no internet transit", which is loose: those bytes crossed the public path from Canada, they just had no third-party endpoint. If 1166 is near the phone's access downlink, the down measurement is characterizing the access link rather than the tunnel, and the 3.3x would be an access-link property that no gateway change can move. Free test, already available in the app: compare the public-family **upload** number against 358. If the public path also caps near 350 to 400, everything below is moot. (UNVERIFIED-LIVE: the phone's public-path upload capacity, and whether it was on Wi-Fi or cellular.)

**What the 2-slot data point actually proves.** Two streams reached 242 Mbps (121 per stream); thirty-two reached 358 (11.2 per stream). Sixteen times the concurrency bought 1.48x. That is a textbook shared-rate saturation curve and it rules out per-flow window limits. It does not localize the shared resource. Radio airtime, phone CPU, and a single gateway drain loop all produce this identical shape.

**Ranked candidates, after the access link is excluded:**

1. **Client egress cost on the phone.** Ingress requires the phone to read TUN, cross the seam, encrypt, and send UDP. That is the most expensive path on the weakest CPU in the system, and mobile SoCs thermally throttle across an 8 s burst. Highest remaining prior.
2. **Gateway per-session driver loop.** Rough pps, assuming ~1400 B inner packets (UNVERIFIED-LIVE: negotiated inner MTU): egress ~104 kpps, ingress ~32 kpps, so ~31 us per packet in the drain. That is far above AEAD cost plus a single write syscall, which means either the loop does per-packet syscalls where the egress side batches, or it is paying channel handoffs and scheduler wakeups per frame.
3. **Gateway demux / UDP receive loop.** Ingress-only, single-consumer, same structural shape as (2). Indistinguishable from (2) without a counter.
4. **Inbox 256 tail drops.** An amplifier, not the ceiling. At the observed 32 kpps drain, 256 frames is about 8 ms of buffering, roughly an eighth of one RTT. Drops do not cap goodput below the drain rate on their own; they force TCP to settle *under* it, and synchronized tail-drop across 32 flows settles it well under.
5. **AF_UNIX batch 256.** Weak. The same seam carries ~104 kpps in the down direction, so 256-frame batching is demonstrably not a 32 kpps limiter.
6. **Client SO_SNDBUF 8 MiB.** Effectively ruled out. On a UDP carrier socket SO_SNDBUF bounds a momentary queue, not steady-state rate; 8 MiB is ~180 ms of buffering at 358 Mbps, so it is oversized rather than limiting. A shortage would surface as ENOBUFS, not as a smooth plateau.

**Cheapest discriminating measurement (no code change).** During one upload run on the Canada node, sample `nstat` or `netstat -su` for UDP receive buffer errors, plus `ip -s link show winn3gw0` for TX drops, before and after. Three-way split: kernel UDP receive drops non-zero means the demux loop is not draining the socket, so (3) is the ceiling. Kernel clean but app inbox dropping means (2). Both clean means the ceiling is upstream of the gateway entirely, which sends you to (1) and to the access link. One shell sample resolves what a deploy cycle otherwise guesses at.

**Cheapest code change:** an atomic counter plus high-water mark on the per-session inbox, exported with existing stats. One line each, and it converts candidate (4) from speculation to a number.

**Batch 256 to 512: NO, and it plausibly makes ingress worse.** Two reasons. First, batch size is a client-internal parameter; if the ceiling sits at the gateway drain, changing it cannot move anything, because the gateway never observes the client's framing granularity. Second, and more specific: the client's 256-frame batch becomes a near-back-to-back burst of encrypted datagrams on the wire, and it arrives at a gateway inbox that is also 256 deep. Batch size equal to queue depth means one batch exactly fills an empty inbox, and any batch arriving with the inbox non-empty tail-drops. Raising the client batch to 512 against an unchanged 256 inbox guarantees loss on every batch, trading a few syscalls for synchronized TCP collapse across 32 flows. (UNVERIFIED-LIVE: how much intermediate path pacing smears the burst; over a clean high-capacity path, assume it largely survives.) If these get touched, the gateway inbox moves first and alone (256 to 2048), measured, and only then the batch, and never the batch ahead of the inbox.
