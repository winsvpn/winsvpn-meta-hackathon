I'm shaping the Podium 4 response with a punchy opening position, then breaking down the root cause around IPv6 tunneling, planning to back it with kernel datapath details, MTU budget math, and a VpnService code analysis.

On the technical substance, I'm weighing whether the IPv6 issue is a routing correctness bug rather than a throughput problem, and whether the fix belongs in the VpnService route table or as IPv4 pinning at the app layer. I'm also working through the tradeoff of removing the IPv6 default route versus properly signaling no IPv6 capability, since simply dropping the route risks leaking traffic outside the tunnel unless the tun interface is also stripped of an IPv6 address so Android's connectivity stack reports no v6 capability for that network.

I'm digging into how Android's DNS resolver actually decides whether to return AAAA records :  it relies on AI_ADDRCONFIG, which checks IPv6 connectivity via a UDP connect test that could falsely succeed just because a route exists, even without real reachability.

That points to two possible fixes: strip the ::/0 route entirely, or properly configure IPv6 addressing on the tun interface. I'm also weighing whether the packet loss reported is due to a missing source address on the tun (which would normally throw an error) versus the gateway silently dropping traffic, since ping showed loss rather than an outright failure :  pointing me toward a two-layer solution starting with the VPN-side fix.

Rather than just gating the ::/0 route on gateway v6 capability (which risks a leak if handled wrong), I'm leaning toward a cleverer approach: keep the route but have the tunnel service intercept any IPv6 packet from the tun and immediately respond with an ICMPv6 "no route" unreachable message. That forces connect() to fail instantly with ENETUNREACH instead of hanging for the usual timeout, letting apps fall back via Happy Eyeballs right away while still preserving leak protection. I think this fast-fail sink is the better primary fix to propose.

But I'm second-guessing whether Android's getaddrinfo with AI_ADDRCONFIG would even resolve AAAA in this scenario, and I need to check how VpnService.Builder's allowFamily interacts with default routing behavior when a family has no explicit route :  I want to make sure I understand whether IPv6 traffic gets blocked by default or bypasses the VPN entirely in that case.

With a getaddrinfo AAAA lookup failing fast, that confirms no IPv6 path exists. So the main fix is dropping the IPv6 route when the gateway lacks v6, letting Android's default-block deliver a quick ENETUNREACH, with pinning IPv4 for the speed test as a backup measure -- I want to avoid relying on preferIPv4Stack since Android's libcore doesn't reliably honor that system property.

Since connecting directly to a literal IPv4 address for HTTPS would break SNI and hostname verification with HttpURLConnection, I think the cleaner approach is using OkHttp's custom Dns interface to filter results to IPv4 addresses while keeping normal hostname-based connection semantics intact.

Now I'm shifting to the MTU budget question, working out the encapsulation overhead for Wi-Fi's 1500-byte MTU with the outer IPv4 header taking its 20 bytes.

I'm calculating the tunnel overhead: assuming a 1420-byte tun MTU like WireGuard uses, the inner TCP MSS becomes 1380, giving roughly 92% goodput efficiency, then figuring out packets-per-second at gigabit speeds to estimate the per-packet processing budget on the device, which comes out to about 11.4 microseconds including the read syscall, encryption, and send :  pointing toward batching multiple packets per TUN read to hit that budget.

Since Android's VpnService doesn't expose GSO or multi-packet reads on the tun fd, and the MTU is capped by the physical path, the encryption workload has to be spread across the handset's cores instead :  modeling ChaCha20-Poly1305 throughput at roughly 1.5 GB/s per core against the 125 MB/s needed for gigabit uploads to see how much CPU headroom that leaves.

The real bottleneck turns out to be syscall overhead: at ~176k combined read/sendto calls per second, that's already a third of a core, so batching UDP egress with sendmmsg to send 16 packets at once cuts that down to about 5.5k calls per second. Then I work out per-stream TCP buffering by estimating bandwidth-delay product at gigabit speeds with a 10ms RTT, concluding 24 parallel streams is more than the bandwidth strictly needs but gives useful resilience against loss, and I start weighing the overhead of chunked encoding per 256KB chunk.

Chunk header overhead is negligible, so I'm confirming that HttpURLConnection's chunked streaming mode buffers full 256KB before writing. The trickier issue is measurement lifecycle: bytes written to the socket aren't the same as bytes confirmed received, since Cloudflare's endpoint only returns 200 after receiving the whole body, and if streams get killed mid-flight the naive confirmed-byte count is zero. I'm proposing to count bytes right after each flush() call succeeds, treating that as accepted-by-kernel, then correct for the unacked tail using the socket's send buffer size, or alternatively use a time-boxed approach where each stream writes for a fixed duration, closes with a terminating chunk, and reads the response code with a short timeout to confirm completion.

I'm setting the shutdown deadline to account for duration plus connect and read timeouts plus margin, and specifying graceful executor shutdown with per-stream deadlines rather than an abrupt kill.
