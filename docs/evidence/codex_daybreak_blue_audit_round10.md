### DB-03: Medium, SQLite WAL runtime is not version-gated

**Affected area:** generated Kansas control plane in `server/wins_control_plane_setup_ONETOUCH.sh:7265`

**Root cause:** Every DB connection executes `PRAGMA journal_mode=WAL`, while background workers and request handlers use distinct connections. The installer accepts the distribution SQLite without a startup version check. SQLite documents a rare WAL reset corruption defect affecting versions from 3.7.0 through 3.51.2, fixed in 3.51.3 and selected backports 3.50.7 and 3.44.6. The audit Python used SQLite 3.53.4 and is not affected, but the deployed Kansas runtime version was not available for read-only verification.

**Exact production repair:** Add this immediately after importing `sqlite3` in the generated control-plane Python:

```python
def sqlite_wal_reset_fix_present(version: tuple[int, int, int]) -> bool:
    padded = tuple(version[:3]) + (0,) * max(0, 3 - len(version))
    current = padded[:3]
    return (
        current >= (3, 51, 3)
        or (3, 50, 7) <= current < (3, 51, 0)
        or (3, 44, 6) <= current < (3, 45, 0)
    )


if not sqlite_wal_reset_fix_present(sqlite3.sqlite_version_info):
    raise RuntimeError(
        "SQLite " + sqlite3.sqlite_version
        + " is unsafe for concurrent WAL use. Require SQLite 3.51.3+, "
        + "3.50.7, or 3.44.6 before starting the hub."
    )
```

Also pin the server image or package source to one of those safe branches. The startup guard is required even when packaging is pinned because it verifies the runtime actually imported.

## 5. Performance and memory assessment

No evidence supports a broad performance claim. The code has several sound bounds:

- QUIC receive windows are capped and their supplied configuration is copied rather than mutated.
- Winn v3 UDP sockets request larger send and receive buffers and have tests that inspect the actual socket values.
- Linux and Windows v3 paths compute an inner MTU from the widest advertised carrier plan, reject mismatches and oversized packets, and avoid unbounded packet allocation.
- Android no longer holds a full-session Wi-Fi performance lock. Its startup wake lock is time-bounded.
- iOS has a 15 MiB physical-footprint watchdog.
- Process and IPC reads use explicit byte ceilings and timeouts on reviewed paths.

Open performance work must be measurement-led:

1. Run 30-minute UDP and TCP profiles at 64-byte, 512-byte, and near-MTU packets on every target architecture. Record throughput, p50, p95, p99 latency, loss, CPU, wakeups, RSS, and energy impact.
2. Repeat with network transitions, carrier fallback, packet reordering, and constrained receive buffers.
3. On iOS, record PacketTunnel physical footprint at one-second resolution. Passing means the maximum remains below 15 MiB without watchdog cancellation.
4. On Android, use Battery Historian and Perfetto for connected idle, screen-off, reconnect storms, and split tunneling.
5. On Linux and Windows, run FD and handle census before connect, after 100 connect cycles, and after forced child crashes. Passing means the final count returns to baseline within a fixed small tolerance.
6. Test path MTUs 1280, 1360, 1420, 1450, 1492, and 1500 with IPv4 and IPv6. Passing means no fragmentation loop, black hole, or payload above the published inner MTU.

No socket-buffer increase or crypto tuning is recommended before these profiles. Larger buffers can violate the iOS memory budget and increase latency under loss.
