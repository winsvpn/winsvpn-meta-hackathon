# Apple Platform Implementation Plan

Last reviewed: 2026-08-24

This is the implementation track for macOS and iOS. The current Apple folders are no longer empty shells, but they are still not production VPN clients. Do not publish Apple downloads until the Network Extension work below is fully implemented, signed, and tested on Apple hardware.

## Current signing availability (verified 2026-08-24)

- Usable code-signing identities currently visible in the local keychain are
  Apple Development, Apple Distribution, and Developer ID Application.
- iOS and the embedded watchOS app have substantially complete distribution
  signing/profile inputs, but still require a fresh `1.0.15+30` archive, export,
  artifact verification, and private-symbol custody record.
- macOS App Store packaging is blocked because no `3rd Party Mac Developer
  Installer` identity is currently available and current release-bound macOS
  distribution material has not been proven complete. Developer ID installer
  packaging is separately blocked because no `Developer ID Installer` identity
  is currently available.
- App Store Connect authentication is not configured as a complete external
  key-path/key-ID/issuer-ID set in the current release shell. This document does
  not claim current live API authentication, upload authority, or a current IPA
  or PKG.

## Historical implementation record

The dated entries below record implementation and earlier signing experiments.
They do not override the 2026-08-24 signing-availability checkpoint above, and
historical exports, profiles, keychain probes, or custody records are not current
release-candidate evidence.

- Shared Flutter UI, account activation, legal acceptance, payments, referral, server discovery, and Winn Protocol® UI logic are available to Apple builds through `lib/main.dart`.
- `ios/Runner/AppDelegate.swift` and `macos/Runner/MainFlutterWindow.swift` now register the `wins_vpn/tunnel` native method channel and use `NETunnelProviderManager` as the host-side tunnel manager.
- `ios/Runner/AppDelegate.swift` and `macos/Runner/MainFlutterWindow.swift` validate raw tunnel configs, including the shared runtime config byte ceiling, before saving tunnel preferences, persist a private-key-redacted config into the shared App Group container, pass the full config only as transient Packet Tunnel start options, and store only App Group path/metadata in `NETunnelProviderProtocol.providerConfiguration`.
- The Apple host bridges tag the saved tunnel preference with a Win's VPN manager signature, prefer exact signed preferences on reload, migrate older same-bundle preferences, and remove stale duplicate Win's VPN preferences.
- The Apple host bridges expose a native `loadOrCreateClientKeyPair` method backed by Keychain and CryptoKit X25519 key derivation. Flutter now requires that native key store on iOS/macOS, while non-Apple platforms can still use the existing file-backed key pair path. The shared Swift key store prefers the signed `$(AppIdentifierPrefix)org.winsvpn.shared` keychain access group when available and migrates older app-local key items into it. This prevents Apple activation from using a file-only key that PacketTunnel cannot restore from a redacted App Group config later.
- Runner and PacketTunnel Info.plists now also carry `WinsAppleSharedKeychainAccessGroup=$(AppIdentifierPrefix)org.winsvpn.shared`, and the shared Swift keychain helper reads that expanded value before falling back to macOS-only entitlement inspection. This keeps the shared keychain code compiling for iPhoneOS, where `SecTaskCreateFromSelf` is not exposed through the Swift iOS SDK import, while preserving signed host/extension keychain sharing.
- The iOS host bridge now detects Simulator builds with `targetEnvironment(simulator)` and fails closed before touching `NETunnelProviderManager`. Simulator launches can still exercise Flutter/UI state, but packet-tunnel start/readiness/probe calls report `APPLE_TUNNEL_UNSUPPORTED` / `simulator_unsupported`; signed physical iPhone or iPad builds remain the only runtime path for real Network Extension validation.
- The Apple host bridges expose a native `loadOrCreateInstallId` method backed by Keychain. Flutter now prefers that native install identity on iOS/macOS and falls back to the existing file-backed install ID path only if the native bridge is unavailable. The install identity uses the same shared keychain access group when signing grants it.
- `apple/WinsTunnelCore/WinsTunnelConfig.swift` is shared by the iOS/macOS Runner targets and Packet Tunnel targets so host-side config validation and extension-side config validation cannot drift.
- Before saving Apple tunnel preferences, the iOS/macOS host bridge now verifies that the incoming config's interface private key derives to the Keychain-held client public key. This prevents a stale or server-provided private key from being redacted into App Group storage and later restored with a different Keychain key.
- Before Smart Protocol starts a cached config, Flutter checks that the cached `client_private_key` and `client_public_key` still match the current local/Keychain key pair. If they do not match, it refreshes the config from the hub instead of handing stale key material to the Apple native bridge.
- The host app and Packet Tunnel Provider now exchange sanitized schema-2 runtime status through `Tunnel/latest_status.json` in the App Group. Each start gets a non-secret `status_generation` token, and provider status writes, including stopped status, fall back to the saved generation from provider configuration when needed. The Packet Tunnel Provider also caches the sanitized current generation during start, so later stop/sleep/wake/app-message status writes can stay tied to the same host expectation even if transient start options are gone. The host-side initial `config_saved` status and both iOS/macOS providers call the shared pure Swift `WinsPacketTunnelProviderStatus.payload(...)` builder, while provider runtime writes use `WinsPacketTunnelProviderStatus.writableData(...)` so oversized diagnostic payloads are reduced to a compact, valid status under the host read ceiling. The command-line harness verifies the payload schema, bounded writable status fallback, signed stage allowlist, generation sanitization/fallback, codec-safe byte-count clamping, integer-only numeric sanitization, error redaction, mapped-value sanitization, and raw-config leak resistance outside the Network Extension runtime. `getTunnelReadiness` reads provider status with a shared byte ceiling and returns distinct sanitized diagnostics for missing App Group containers, missing status files, unreadable files, invalid JSON, and oversized status files before parsing. Host-side status file sizes are converted to bounded `Int` values before crossing Flutter method channels, so corrupt App Group files cannot break readiness reporting with unsigned 64-bit metadata. After parsing, the host maps provider status values through `WinsPacketTunnelProviderStatus.safeMappedStatusValue(...)` before forwarding them to Flutter, so malformed status files cannot surface raw paths, URLs, IP literals, config lines, oversized strings, unsupported objects, unsafe numeric values, or unsafe list entries. The early stale-status path uses the same status-generation sanitizer and reports invalid-generation booleans instead of echoing unsafe generation text. It also rejects unsupported provider status schema versions, ignores stale provider status files whose generation does not match the current saved tunnel preference, refuses status whose reported Packet Tunnel bundle identifier does not match the expected iOS/macOS extension, refuses status whose Network Extension type is not `packet_tunnel`, refuses missing or malformed provider `updated_at` timestamps, and refuses provider stages outside `WinsPacketTunnelProviderStatus.knownStages`. The host also passes the expected Apple client public key through provider configuration and transient start options; the Packet Tunnel Provider verifies that the runtime private key derives to that public key before applying Network Extension routes. Readiness includes provider stage/error fields such as `provider_stage`, `provider_error_code`, `provider_network_settings_ready`, `provider_config_source`, `provider_private_key_source`, `provider_client_key_pair_verification_required`, `provider_client_key_pair_verified`, and `provider_default_route_enabled` so physical-device testing can distinguish config, Keychain sharing, Network Extension, route-scope, schema-drift, stale-status, timestamp drift, stage drift, bundle mismatch, extension-type mismatch, key/config mismatch, status-file read failures, bounded status-write fallback, and missing-engine failures. Endpoint-specific readiness data is redacted to host-kind and presence fields, such as `provider_transport_endpoint_kind` and `provider_transport_ipv4_exclusion_route_present`, so support/debug captures do not echo server IPs, paths, or local handoff ports.
- Packet Tunnel app-message handling now returns a sanitized schema-1 health response instead of echoing raw app payloads. The provider accepts only the exact sanitized `health` command for readiness probes, rejects oversized app messages and unsupported or unsafe commands fail-closed, and records safe `app_message_*` plus sleep/wake `lifecycle_*` fields so physical-device testing can identify extension lifecycle transitions without logging message bodies, paths, keys, hosts, or ports. Rejected app messages write an unhealthy provider status even when the engine is otherwise running, while preserving `app_message_engine_running` for diagnostics. Sleep lifecycle writes are also unhealthy while preserving `lifecycle_engine_running`, so the UI does not claim the tunnel is usable while the OS has suspended the extension; wake lifecycle status can become ready again only when the provider reports the engine and network settings ready. When the OS reports an active `NETunnelProviderSession`, the iOS/macOS host bridge sends a timeout-bounded schema-1 health message and gates Apple readiness on the sanitized provider response if that probe was attempted; the shared `WinsPacketTunnelProviderAppMessage.healthProbeResponseStatusFields(...)` parser rejects oversized or invalid JSON responses before interpreting fields and represents timeouts/send failures as redacted zero-byte response diagnostics. The probe is considered healthy only when the response command is sanitized to `health`, the command is marked as the health command, the schema version matches, the provider reports the engine running, and `raw_payload_redacted` is true. The shared Swift and Dart readiness helpers also refuse an `app_message` provider status unless it was accepted, marked as the health command, and raw-payload-redacted, and refuse suspended lifecycle status.
- The Apple host bridges now implement the shared `showAnnouncementNotification` method with native `UserNotifications` on iOS and macOS. Shared Swift `WinsAppleNotification` logic trims and bounds announcement title/body values before scheduling, rejects empty bodies, applies the default Win's VPN announcement title when needed, and is covered by the command-line Apple harness. Notification permission is requested only when needed, and the native bridge returns `false` without logging announcement text if the user denies notifications.
- iOS and macOS now use the native `launchExternalUrl` bridge for public app links instead of falling through to platform command-line launchers. The shared Swift `WinsAppleExternalUrl` validator trims and bounds URLs, rejects internal whitespace/control characters and userinfo, permits only explicit external schemes (`http`, `https`, `mailto`, `tel`, and `sms`), requires hosts for web URLs, requires non-empty direct payloads for mail/phone/message schemes, constrains `tel`/`sms` destinations to phone-safe characters, and rejects local/script/file-style payloads before UIKit/AppKit opens anything. The command-line Apple harness covers accepted public URLs and rejected local/script/file, empty-payload, whitespace, userinfo, unsafe direct-scheme payload, and host-style phone/message payloads.
- iOS and macOS referral sharing now routes through the native `shareText` bridge instead of falling back directly to clipboard copy. Shared Swift `WinsAppleShare` logic trims and bounds share titles/text, rejects empty share text, and feeds only sanitized payloads to `UIActivityViewController`, `NSSharingServicePicker`, or the macOS pasteboard fallback. The command-line Apple harness covers blank, trimmed, title-less, and oversized share payloads.
- Packet Tunnel provider logs now use host-kind/presence/count summaries instead of exact endpoints or interface addresses. Provider status still includes exact error domains and numeric codes, but generic Apple/system error messages are redacted before reaching `provider_error`; controlled `org.winsvpn.*` validation and engine messages keep their detailed text only after the shared diagnostics helper confirms they are bounded and do not contain raw paths, URLs, IP literals, UUID-like identifiers, config lines, or key fragments. The iOS/macOS Runner method-channel bridge uses the same shared diagnostics helper so Apple system errors returned through Flutter errors, readiness dictionaries, probe results, or stale-manager cleanup logs do not expose local paths or raw OS text. Runner-side Flutter error details and readiness/probe payloads include structured `native_error_domain` and `native_error_code` fields so support can triage Apple failures without raw localized OS messages.
- iOS and macOS now include `PrivacyInfo.xcprivacy` manifests for both Runner and PacketTunnel bundles. Host app manifests declare account/device identifiers as linked, non-tracking data used for app functionality, plus required-reason API access for app-container file metadata and app defaults. PacketTunnel manifests declare no collected data and only the required file-metadata API reason used by bounded config/status file checks. `tools/verify_apple_readiness.sh` validates the source manifest contract, and `tools/apple_runtime_smoke.sh` verifies that built host apps and embedded PacketTunnel extensions actually contain the manifests in the expected bundle locations.
- The Dart Apple diagnostics layer now applies its own fail-closed sanitizer to provider scalar values, component lists, status generations, and native bridge error summaries before producing debug text. This mirrors the Swift provider-status sanitizer so malformed method-channel values cannot leak raw paths, IPv4/IPv6 literals, plain hostnames, UUID-like identifiers, URLs, config lines, key fragments, oversized component names, or unsafe native exception messages into app logs or support summaries even if a future native payload bypasses the expected Swift mapping.
- `ios/PacketTunnel` and `macos/PacketTunnel` now contain Packet Tunnel Provider source scaffolds, Info.plists, and Packet Tunnel entitlement files. The provider can load config from transient start options, can restore a redacted App Group fallback config from the shared Keychain client key when the keychain access group is signed correctly, validates the Win's VPN config shape and runtime config byte ceiling through the shared parser, builds and applies Apple `NEPacketTunnelNetworkSettings` with the real transport endpoint as `tunnelRemoteAddress`, normalized `AllowedIPs` IPv4 routes, deterministic IPv4 transport endpoint exclusions for full-tunnel routes, full-tunnel DNS match domains, DNS servers, MTU, and an IPv6 fail-closed default route for full-tunnel configs, and then fails safely until the AWG/Xray packet engine is bundled. Provider config handoff reads are bounded through a shared UTF-8 file reader, reject symbolic-link handoff files, and stored `shared_config_path` values are accepted only when they resolve to the exact App Group `Tunnel/latest_tunnel.conf` handoff file. App Group identifiers from saved tunnel preferences are accepted only when they match the expected shared App Group before the provider processes transient start configs, reads fallback configs, or writes status. The provider also prefers saved tunnel-preference `client_public_key` and `status_generation` values over transient start-option values, using transient values only as fallback, so key verification and readiness correlation stay bound to the installed tunnel preference. Provider status reports whether the expected Apple client public key is available and valid, plus a redacted source label for saved preference, transient start option, host Keychain, or missing metadata, without logging the key itself; device tests can distinguish malformed key metadata from private-key mismatch or missing shared Keychain access. Host-side provider readiness reads also reject symbolic-link `latest_status.json` files before parsing. Host and provider App Group writes use a shared atomic file writer that replaces symbolic-link handoff directories/files without following them and reapplies private file permissions. Start-rejection status reports sanitized config source/read/path diagnostics for oversized files, unreadable files, symbolic-link files, invalid UTF-8, empty files, rejected handoff paths, rejected App Group identifiers, missing App Group containers, missing shared Keychain private keys, and missing tunnel config without logging paths, App Group identifiers, or config contents. Provider status distinguishes `network_settings_failed` from the expected temporary `engine_missing` state and reports sanitized IPv6 leak-protection booleans without exposing the local sink address.
- The shared Apple parser now validates the AmneziaWG obfuscation fields and full Xray fallback handoff (`Uuid`, host, port, server name, path, security, local port, and remote AWG loopback target). PacketTunnel status exposes `transport_mode`, `required_engine_components`, `engine_bundle_probe`, and sanitized bundle component lists, so iPhone/macOS testing can tell whether a failure is config drift, missing native AmneziaWG packet engine, missing Xray transport, all signed engine artifacts being present but the adapter still unwired, or Apple Network Extension setup.
- The native Xray VLESS-WebSocket wrapper mirrors the Swift-side launch validation before writing the process-local Xray config. It now rejects missing or malformed UUID, host, port, server name, path, security, local handoff port, remote AWG host, and remote AWG port fields instead of substituting fallback defaults inside the Packet Tunnel extension.
- `apple/WinsTunnelCore/WinsPacketTunnelEngine.swift` centralizes the current PacketTunnel native-engine integration boundary for both iOS and macOS. Until a signed native AmneziaWG/Xray engine adapter is implemented, both Apple extensions create engines through `WinsPacketTunnelEngineFactory`, run through the same `WinsPacketTunnelEngine` lifecycle protocol and `WinsMissingPacketTunnelEngine`, and report structured missing-engine status through that shared path. The factory now probes the Packet Tunnel extension bundle for known signed AWG/Xray artifact names and reports only sanitized component identifiers, never file paths or bundle paths. It also exposes a fail-closed `WinsPacketTunnelEngineAdapter` injection contract: the factory will not invoke an adapter unless every required signed component is present, adapter-backed engines keep the factory's validated plan, adapter runtime status is filtered to safe `engine_runtime_*` scalar/list fields, and adapter-backed starts override `engine_adapter_available` only after the wrapped engine starts. The engine plan also emits a non-secret launch contract version, a first-class `WinsPacketTunnelEngineLaunchDescriptor`, a sanitized bundle probe (`engine_bundle_required_components`, `engine_bundle_available_components`, `engine_bundle_missing_components`, and `engine_bundle_all_required_components_present`), and sanitized runtime-shape fields such as packet-flow requirement, route/DNS counts, endpoint kinds, Xray requirement, key-material redaction flags, AWG obfuscation field count, and Xray field presence. This gives the future native adapter a clear handoff boundary without leaking private keys, peer keys, raw hosts, paths, ports, UUIDs, local file paths, or bundle paths into support diagnostics.
- Native adapter start diagnostics now preserve sanitized component-start booleans for AWG and Xray. If Xray starts but the AWG packet engine fails, or either component rejects its launch boundary, iOS/macOS readiness and Flutter debug summaries expose only `engine_runtime_xray_started` and `engine_runtime_awg_started` booleans so live-device testing can isolate the failing native component without leaking endpoints, keys, paths, ports, UUIDs, or local loader paths.
- The iOS and macOS PacketTunnel Xcode targets now run `tools/stage_apple_engine_artifacts.sh` during extension builds. Signed local artifacts can be placed under `apple/EngineArtifacts/ios/iphoneos/`, `apple/EngineArtifacts/ios/iphonesimulator/`, or `apple/EngineArtifacts/macos/`; the script removes stale copied artifacts, rejects symlinks, verifies Mach-O platform and architecture metadata, optionally code-signs copied artifacts with Xcode's active identity, writes a non-secret manifest, and fails production gates when `WINS_REQUIRE_APPLE_ENGINE=1` and either required component is missing. Actual binaries are gitignored and must stay local or in a secure artifact store.
- Flutter now polls Apple `getTunnelReadiness` during tunnel startup instead of treating iOS/macOS as a simple connected-state check. Provider stages such as `engine_missing`, `network_settings_failed`, and `start_rejected` are preserved in debug logs, while the user-facing status remains clean and does not expose transport internals.
- Flutter now also uses provider-aware Apple readiness when restoring native tunnel state after app launch, foreground resume, status heartbeat checks, server switching, and live-network label refresh. iOS/macOS no longer treat raw Network Extension `connected` state as enough to restore the UI to "secured"; the Packet Tunnel provider status must be current and healthy through `appleTunnelReady(...)`.
- Apple host readiness now keeps host-level `engine_ready`, `tunnel_healthy`, and `vpn_validated` false until the Packet Tunnel Provider reports current provider-prefixed readiness. The host still exposes `network_extension_connected` so tests can distinguish an OS-level Network Extension connection from real packet-engine health.
- Flutter's post-start `_confirmTunnelUsable` check now follows the Apple provider-prefixed readiness contract too: it uses `provider_engine_ready`, `provider_healthy`, `network_extension_connected`, and `appleTunnelReady(...)` on iOS/macOS instead of requiring the generic host-only readiness flags that stay false until provider health is proven. The native iOS/macOS `probeVpnInternet` bridge also merges current provider readiness and health-probe diagnostics into its response and refuses to run the public HTTPS probe until shared `WinsAppleReadiness.providerReady(...)` passes, returning `internet_probe_blocked_by_provider_readiness` when the OS-level Network Extension is connected but the Packet Tunnel provider is not yet trustworthy. Before that public HTTPS probe is trusted, the bridge also requires a conservative full-tunnel leak-protection config gate: current provider status, default route enabled, provider and engine IPv6 leak protection enabled, provider and engine full-tunnel DNS match enabled, and provider/engine DNS server counts greater than zero. Failures return `internet_probe_blocked_by_leak_protection_config` and sanitized `leak_protection_*` fields instead of claiming an external DNS canary was performed. Dart now preserves those probe fields in sanitized debug summaries, including provider-current/provider-ready state, leak-protection config state, probe-attempt state, URL kind, and HTTP status code without logging the raw probe URL, DNS server, endpoint, or app URL.
- Packet Tunnel Provider lifecycle/app-message status writes now retain the active parsed config while the tunnel is alive. This keeps route, DNS, IPv6, transport, and engine-plan diagnostics present after health checks, sleep/wake transitions, and stopped status writes instead of thinning out the latest provider status file after an app-message probe.

## Required Native Architecture

Apple VPN apps must use `NetworkExtension`; they cannot create raw TUN interfaces like Linux or run arbitrary privileged helper behavior like desktop Windows installers.

Required targets:

- `Runner` iOS app.
- `Runner` macOS app.
- `PacketTunnel` iOS extension with `PacketTunnelProvider`.
- `PacketTunnel` macOS extension with `PacketTunnelProvider`.
- Optional shared Swift package or framework for config parsing, key handling, Xray/AWG orchestration, and diagnostics.

Required entitlements:

- Network Extension Packet Tunnel entitlement for iOS and macOS.
- App Groups for passing the generated VPN config from the Flutter app to the Packet Tunnel Provider.
- Shared Keychain access group for device/install identifiers and private client key storage. The local source uses `$(AppIdentifierPrefix)org.winsvpn.shared` for Runner and PacketTunnel targets.

## Method Channel Contract

The Apple app must implement the same channel used by Android, Windows, and Linux:

- Channel: `wins_vpn/tunnel`
- `getTunnelState` -> `bool`
- `startTunnel` with `{ "config": "<generated config>" }` -> starts or updates `NETunnelProviderManager`
- `stopTunnel` -> stops active tunnel
- `getAppDocumentsDirectory` -> app-private documents/support directory when needed
- `getDeviceHardwareDetails` -> privacy-preserving install/device model fields
- `launchExternalUrl`, `shareText` -> native Apple share/open helpers

iPhone and iPad implement the disclosed functional Calculator safety screen and a bundled Calculator alternate home-screen icon through Apple's supported alternate-icon API. The user's configured four-digit PIN restores the VPN interface and primary Win Empire icon; macOS does not use calculator camouflage.

## Tunnel Engine Strategy

Preferred v1:

- Use Apple `NEPacketTunnelProvider` as the packet interface.
- Port the existing AWG/Xray config format parser into Swift.
- Run the censorship-resistant transport inside the Packet Tunnel Provider process or a bundled native library approved for App Store distribution.
- Store no browsing history, DNS query history, traffic contents, or destination metadata.
- Report only coarse tunnel state/error codes back to the app.

Open engineering questions:

- Whether AmneziaWG client code can be bundled under its license and Apple review constraints.
- Whether Xray can be bundled/executed in a Network Extension in a way that passes App Store review.
- Whether Smart Boost will be Apple-approved, since binding simultaneous Wi-Fi/cellular paths may require careful Network framework implementation and review.
